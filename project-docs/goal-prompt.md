# 새 세션용 기본 기능 완성 Goal

- 작성일: `2026-09-18`
- 용도: 새 세션에서 기본 기능 구현을 시작하거나 이어가기 위한 실행 프롬프트
- 제품 범위의 기준은 [PRD](prd.md)와 [로드맵](roadmap.md)이다. 이 문서는 별도 PRD·구현 계획·완료 기록이 아니다.
- 이 파일의 작성 자체는 Goal 실행이나 실제 인프라 변경을 시작하지 않는다.

## 사용 방법

Gjallar 저장소를 연 새 세션에서 아래 짧은 시작문을 입력한다. 파일을 읽을 수 없는 세션에는 다음 절의 전체 프롬프트를 `/goal` 뒤에 붙여 넣는다.

```text
/goal project-docs/goal-prompt.md의 ‘실행 프롬프트’를 읽고 그 지시에 따라 Gjallar 기본 기능 완성 작업을 시작해. 현재 문서와 코드를 확인하고, 승인된 범위에서 구현·검증·문서 갱신을 계속해.
```

## 실행 프롬프트

```text
Gjallar의 기본 운영 기능을 웹과 CLI에서 실제로 사용할 수 있도록 완성해줘. 이 목표를 Goal로 관리하고, 승인된 범위의 구현·검증·문서 갱신을 지속해.

1. 먼저 현재 상태를 확인해

- AGENTS.md와 project-docs/development.md를 읽고 작업·검증·운영 경계를 확인해.
- project-docs/prd.md, roadmap.md, 관련 architecture.md 계약과 현재 work 기록을 확인해. archive와 종료된 계획을 새로운 구현 권한으로 해석하지 마.
- git status와 관련 diff를 확인해 미커밋 변경을 보존해. 이미 완료된 작업을 다시 구현하거나 다른 작업의 변경을 되돌리지 마.
- 문서의 구현·검증 주장과 현재 코드를 대조해. 과거 테스트 통과를 현재 checkout의 검사 결과로 사용하지 마.
- 재개 세션에서는 로드맵이 연결한 진행 중 work의 ‘재개 지점’을 먼저 읽고 현재 코드·diff·실행 상태와 대조해. 완료한 기능을 다시 시작하거나 결과가 불명인 외부 작업을 다시 실행하지 마.
- 먼저 현재 상태, 다음 실행 범위, 검증 방법을 짧게 설명하고 실제 작업을 진행해. 계획 제시만으로 끝내지 마.

2. 완성할 사용자 경험

- 첫 버전은 웹 + CLI야. 기존 TUI는 보존하고 신규 기능 동등 지원과 TUI 개선은 후속으로 둬.
- 각 기능은 대상 선택 → 입력·영향 확인 → 실행 → 실제 결과 확인까지 이어져야 해. 서버/API만 구현하고 기능 완료로 처리하지 마.
- 2026-09-20에 승인한 UI 전면 개선을 진행해. 대시보드도 개편할 수 있고 상단 탭 네비게이션을 명확히 정리해. 실제 화면을 직접 확인한 뒤 중복 메뉴·흩어진 작업·과도한 정보를 정리하고 기존 기능·canonical URL·권한·실행 동의는 보존해.
- 현재 화면에서 유지할 것, 합칠 것, 상세로 옮길 것을 정하고 공통 탐색과 VM 상세 구조를 먼저 구체화해. 실제 화면을 보지 못했다면 UI 평가의 한계를 밝혀.
- VM 관련 작업은 VM 상세에서 이어가고, 현재 상태·결과·다음 조치를 먼저 보여줘. 상세 기록과 진단 정보는 필요할 때 확인하게 하되 실행 영향·경고·동의는 숨기지 마.
- 전체 화면 개편을 별도 선행 프로젝트로 만들지 말고 각 기능 구현과 함께 필요한 화면을 완성해. 웹과 CLI가 동일한 모양일 필요는 없지만 같은 권한·작업·결과를 사용해야 해.

3. 실행 순서와 범위

최신 roadmap.md의 범위와 상태를 기준으로 다음 업무를 진행해. 아래 목록은 방향 요약이며 상세 계약은 현재 문서와 해당 구현 work를 따라.

- M1 설치·연결: 현재 사용할 환경에서 설치 또는 기존 서버 접속, 로그인, Proxmox 연결, 실제 자원 조회, 재시작과 계정·설정·이력 보존.
- M2 VM 일상 관리: 기존 생성·조회·시작·정상 종료 보완, CPU·메모리 변경, 디스크 확장, NIC 설정 변경, 복제, 삭제, 웹 콘솔. CLI는 웹 콘솔 진입을 안내해.
- M3 템플릿: 준비된 VM의 템플릿 전환, 공식 cloud image 한 종류로 제작, 테스트 배포·검사·명시적 정리.
- M4 모니터링: 현재 사용량, PVE 제공 이력을 우선 활용한 추이, 제품 내부의 이상 상태·알림 이력.
- M5 백업·복구: 지원 저장소의 백업 조회·실행, 별도 VMID로 복원과 결과 확인.
- M6 유지보수: 지원 조건에서 정지 VM의 수동 노드 이동, 노드 작업의 영향과 준비 상태 확인.

M1의 사용 경로와 M2를 먼저 완성해 실제 사용을 시작할 수 있게 하고 M3~M6를 추가해. M2 완료를 전체 제품 완료로 표시하지 마. 모든 OS·PVE·storage 조합, 자동 DRS, 다중 클러스터, AI, 기업용 조직·SSO, 자체 범용 TSDB와 백업 엔진은 첫 버전 목표에 추가하지 마.

로드맵에 남은 초안과 미정 사항은 승인된 사실로 간주하지 마. 첫 지원 환경과 OPS-03 호스트 설정 변경 포함 여부처럼 제품 경계를 바꾸는 결정은 초기에 묶어서 질문해. 이미 답한 내용은 다시 묻지 마. 코드 조사로 정할 수 있는 일반 구현 선택은 기존 관례와 가장 단순한 해법을 따라. 답변과 독립적인 조사·준비·승인 범위의 구현은 계속해.

4. 기능별 구현 방식

- 이미 있는 코드·helper·API·UI·테스트를 재사용하고 요청과 무관한 리팩터링·추상화·의존성 도입을 피해야 해.
- 현재 관리형 연결이 read/선택적 power만 지원하는지 코드로 확인하고, 생성과 신규 변경에 필요한 최소 권한 및 기존 연결 갱신 경로를 해당 기능의 필수 작업에 포함해. env 우회나 과도한 권한 확대를 해법으로 삼지 마.
- 첫 M2 실행 단위는 관리형 연결에서 정지 VM의 CPU·메모리를 웹과 CLI로 변경하고 결과를 확인하는 흐름으로 구체화해. 기존 생성·전원 흐름의 권한 공백도 M2 필수 작업으로 추적해.
- 지금 착수하는 의미 있는 작업만 하나의 work 문서에 목표·지원/제외 범위·필요 계약·구현 순서·완료 조건·검증·실패/복구 방법을 작성하고 결과를 이어 기록해. 모든 후속 작업 문서를 미리 만들지 마.
- DB·인증·권한·idempotency·target lock·lease·복구 등 고위험 변경은 저장소 지침대로 구체적인 범위·검증·복구 계획을 먼저 정해.
- 정상 흐름과 함께 잘못된 입력, 권한 거부, 실행 전 상태 변경, 중복 요청, 부분 실패, 연결 단절, 결과 미확정을 처리해.
- API 접수·task 발급만으로 성공을 표시하지 마. 실제 상태를 확인하고, 미확정 mutation은 자동 재실행하지 마. 기존 기록 보존과 GET-only 복구 계약을 유지해.
- 승인된 일반 구현과 검증은 매번 계속할지 묻지 말고 이어가. 사용자 결정이 필요한 사항과 현재 막힌 이유는 구체적으로 알려줘.

5. 검증과 운영 경계

- project-docs/development.md에 따라 변경에 적합한 테스트·lint·build·직접 동작 검사를 실행해. UI 변경은 가능하면 브라우저에서 주요 흐름도 확인해.
- git diff --check, pnpm run verify, pnpm run verify:container를 필요한 완료 지점에서 수행하고 실제 결과를 기록해. 수정 후 관련 검사를 다시 수행하되 근거 없이 같은 전체 검사를 반복하지 마.
- 실제 Proxmox 변경·삭제·설치·배포·운영 DB 변경은 정확한 대상과 영향을 밝히고 필요한 별도 승인을 받아. 과거 승인을 다른 대상이나 작업에 재사용하지 마.
- 실환경 승인 대기 중에는 해당 검증을 미완료로 남기고, 그 결과에 의존하지 않는 승인 범위의 구현·자동 검증을 계속할 수 있어. 시간이 지났다는 이유로 승인받았다고 간주하지 마.
- 시크릿을 대화·코드·문서·로그에 남기지 마. 비밀번호와 토큰은 제품의 적절한 비밀 입력 경로로 처리해.
- 커밋·푸시·배포를 묵시적으로 진행하지 마. 현재 작업 범위는 구현·검증·문서 갱신이야.

6. 기록과 종료 조건

- 기록은 큰 마일스톤이 끝날 때까지 미루지 마. 의미 있는 기능·검증 묶음이 끝났을 때, 중요한 결정이나 차단 사유가 생겼을 때, 마일스톤 종료 때, 사용자의 중단 요청이나 세션 인계 전에는 현재 work를 갱신해. 갑작스러운 종료 직전 저장은 보장할 수 없으므로 진행 중에도 남겨.
- 진행 중 work 한 파일의 ‘재개 지점’에 마지막 갱신 시점, 현재 M/기능 ID, 완료한 내용, 수정한 주요 파일, 실행한 검증과 결과·미실행 항목, 진행 중/미확정 작업, 승인 범위·대기 사항, 다음에 할 구체적인 행동을 기록해. 외부 작업은 시크릿 없이 Operation ID와 상태 확인 방법을 남겨. 기록에 없는 작업은 현재 상태를 조사한 뒤 이어가.
- M1~M6 각 마일스톤을 마칠 때 해당 work에 사용자 관점의 결과·검증 근거·제한·남은 일을 요약하고 로드맵 상태와 근거 링크를 갱신해. 구현만 끝나고 실환경 검증이 남으면 ‘구현 검증 완료 / 실환경 검증 대기’처럼 구분하고 전체 완료로 표시하지 마.
- 새 work를 만들 때 work/README.md에 연결해. 세션마다 새 인계 문서나 별도 완료 보고서를 만들지 말고 기존 작업 문서에 이어 기록해. 기록 갱신은 자동 커밋·푸시를 뜻하지 않아.
- 기능별 서버 구현, 웹/CLI 연결, 자동 검증, 실환경 검증을 구분해 기록해. 실행하지 못한 검사는 이유·남은 위험·재개 방법을 남겨.
- 실제 변경에 맞춰 roadmap.md와 관련 PRD·architecture.md·development.md 및 work 기록을 갱신해. 목표와 현재 구현을 혼동하지 마.
- 의미 있는 진행 상황, 완료한 사용자 흐름, 다음 작업과 막힌 이유를 한국어로 간결하게 알려줘.
- 확정된 M1~M6 범위가 웹·CLI에서 사용 가능하고 필요한 자동·실환경 검증과 사용 문서가 갖춰져야 제품 완료야. 구현만 끝났거나 예산이 부족하다는 이유로 Goal을 완료 처리하지 마.
- 사용자 입력·승인·환경 없이는 더 진행할 수 없다면 완료한 범위와 남은 기능, 정확한 차단 원인과 재개에 필요한 내용을 보고해. 독립적으로 할 수 있는 승인된 작업이 남아 있으면 계속 진행해.
```

## 유지 관리

실행 상태·세부 지원 범위·검증 결과는 이 프롬프트에 복제하지 않고 로드맵과 해당 work 문서에 기록한다. 새 세션은 현재 상태를 확인하고 미완료 지점부터 이어간다. 사용자 결정으로 목표나 실행 원칙이 바뀔 때만 이 프롬프트도 갱신한다.
