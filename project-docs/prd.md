# Gjallar PRD

- 상태: `APPROVED` — 제품 방향. 개별 확장 기능의 구현·배포 완료를 뜻하지 않는다.
- 합의일: `2026-09-16`
- 방향 갱신일: `2026-09-18` — 기본 기능의 웹·CLI 실사용 우선, TUI 개선 후속, 대시보드 유지와 나머지 웹 흐름 정리
- 현재 구현: [아키텍처](architecture.md)
- 순서와 진행 상태: [로드맵](roadmap.md)

## 1. 핵심 가치

**Proxmox 운영에 필요한 일을 갈랴르 한곳에서 쉽게 끝낸다.**

사용자는 갈랴르의 웹이나 CLI에서 템플릿을 준비하고 VM을 만들고 관리하며, 상태를 살피고 문제를 해결한다. 일상 업무를 처리하려고 Proxmox 관리 화면을 반복해서 오가지 않는 것이 목표다. 실제 자원 상태와 저수준 실행은 Proxmox가 담당하며 비상 관리 경로도 유지한다.

## 2. 누구를 위한 제품인가

첫 대상은 자신의 Proxmox 환경을 운영하는 개인과 소규모 인프라팀이다. 설치·연결·기본 운영을 탄탄하게 만드는 데 집중한다. 기업용 조직·결재·규제 준수 기능과 AI를 초기 제품의 전제 조건으로 삼지 않는다.

## 3. 제품 원칙

1. **시작이 쉽다.** 설치에 필요한 조건과 연결 실패 이유를 명확히 안내한다.
2. **일을 끝낼 수 있다.** 지원하는 업무는 대상 확인부터 실행·결과 확인까지 연결한다.
3. **결과를 믿을 수 있다.** 접수·진행·성공·실패·확인 불가를 구분한다.
4. **현재 상태에 근거한다.** 관찰 출처·시점·누락을 표시하고 실행 직전에 필요한 조건을 다시 확인한다.
5. **인터페이스가 달라도 같은 작업이다.** 웹·CLI·기존 TUI는 같은 서버 권한과 검증된 실행 경로를 사용한다. 향후 AI도 이 경계를 따른다.

## 4. 기본 구성과 완료 경험

아래는 제품 목표다. 제공 여부는 로드맵과 현재 아키텍처에서 구분한다. 첫 버전은 웹 + CLI에서 기본 업무를 완료하는 범위이며, macOS·Linux 전체 조합이나 모든 인프라 설정의 동시 지원을 뜻하지 않는다. 첫 지원 환경과 세부 기능 범위는 로드맵·해당 작업에서 정한다.

| 영역 | 사용자가 끝낼 수 있어야 하는 일 | 완료를 판단하는 기준 |
|---|---|---|
| 설치·연결 | macOS·Linux에서 시작하고 Proxmox 연결 | 지원 환경·의존성을 안내하고 연결 상태와 권한 부족 원인을 확인 |
| 템플릿 | 기존 템플릿 등록·조회, 제작·준비·검증 | VM 배포에 필요한 조건의 충족·실패·확인 불가를 표시 |
| VM 관리 | 생성·복제·삭제·전원·사양·디스크·네트워크 관리 | 대상과 변경을 확인하고 실행 후 실제 상태 또는 미확정 사유를 표시 |
| 콘솔 | VM의 화면이나 지원하는 콘솔에 접속 | 갈랴르에서 인증된 세션으로 접근하고 종료 가능 |
| 모니터링 | 노드·VM·스토리지 상태와 사용량·추이 확인 | 마지막 관찰 시점·데이터 누락·실패한 작업을 구분하고 대상 관리로 연결 |
| 백업·복구 | 백업 확인·실행·VM 복원 | 지원하는 복구 단계와 결과 검증, 남은 확인 항목을 표시 |
| 인프라 | 일상 업무에 필요한 노드·스토리지·네트워크 관리 | 지원하는 변경의 영향과 실행 결과를 확인 |
| CLI·웹 | 같은 자원과 작업 관리 | 동일한 권한·작업 ID·진행 상태·결과 사용 |

템플릿은 OS·소프트웨어·기본 설정이며 사양 프리셋은 CPU·메모리 등 기본값·제약이다. 새 템플릿 버전으로 기존 VM이 자동 업데이트되지는 않는다. VM 실행 상태와 애플리케이션 정상 상태, 가상 디스크 확장과 게스트 파일시스템 확장은 각각 구분한다.

### 설치·접속 경험 (`APPROVED`, 부분 구현)

시작 방식은 **이 컴퓨터에서 Gjallar 실행** 또는 **기존 Gjallar 서버에 연결** 두 가지다. 로컬 실행은 bootstrap이 서비스·DB 준비와 최초 계정 설정을 안내하고, 기존 서버 연결은 Gjallar 주소와 Gjallar 계정으로 접속한다. 별도 VM은 필수가 아니며 로컬에서도 Gjallar 서비스가 실행돼야 한다. TUI 종료와 서비스 종료를 구분하고 다음 실행에 사용할 연결을 저장한다.

웹·CLI·TUI는 모두 선택한 Gjallar 서버의 API를 사용한다. 별도 Proxmox 직접 연결 운영 모드는 제공하지 않는다. Proxmox 토큰과 작업 기록은 Gjallar 서버가 관리하며 기존 서버에 접속하는 클라이언트에 Proxmox 토큰을 배포하지 않는다.

공통 client·TUI, 관리형 bootstrap과 아래 Proxmox 연결 핵심 흐름을 구현했다. 현재 관리형 연결은 조회·선택적 시작/정상 종료 권한만 제공한다. 사용자는 2026-09-18 실제 Proxmox 연결 성공을 확인했다. 지원 OS·PVE 버전/인증 조합 전체와 운영 복구까지 검증한 것은 아니며 남은 항목은 [기능 로드맵](roadmap.md)에서 별도로 관리한다.

새 Proxmox 연결은 로그인 → 사용할 기능·대상·필요 권한 안내와 확인 → 전용 토큰 발급·권한 설정 → 안전한 저장 → 토큰으로 첫 자원 조회 순서다. Proxmox 로그인 비밀번호는 저장하지 않는다. 실제 부여 가능한 권한을 검사하며 로그인 성공만으로 발급·권한 설정 성공을 가정하지 않는다. 제품 로그인과 Proxmox 최초 연결은 별개다. 상세 인증·저장·실패 처리 계약은 아키텍처를 따르며, 기능별 권한과 지원 환경은 해당 작업에서 정하고 검증한다.

### 웹 사용 경험 (`APPROVED`, 개편 전)

현재 대시보드의 전체적인 디자인과 구성을 유지하고, 나머지 화면은 기본 운영 업무를 쉽게 찾고 끝낼 수 있도록 정리한다. 실제 화면을 먼저 확인해 중복 메뉴·흩어진 작업·과도하게 노출된 정보를 식별한다. VM 관련 작업은 VM 상세에서 이어가고, 평소에는 현재 상태·결과·다음 조치를 우선 표시하며 상세 실행 기록·진단 정보는 필요할 때 확인하게 한다. 실행에 필요한 영향·경고·동의는 숨기지 않는다.

정확한 메뉴·화면 구성은 현행 UI 검토 후 결정한다. 공통 탐색과 VM 상세 구조를 먼저 정하고 각 기능 구현과 함께 화면을 완성한다. UI 전체를 별도 선행 프로젝트로 만들거나 서버/API만 끝내고 화면 연결을 무기한 미루지 않는다. 웹과 CLI는 같은 업무·결과를 제공하되 화면과 출력 형태를 똑같이 만들 필요는 없다. 첫 콘솔은 웹 접속과 CLI의 웹 진입 안내를 목표로 한다.

## 5. 현재 출발점

웹 기반 inventory와 VM 상세, Insights, 기존 템플릿 복제 기반 생성, 시작·정상 종료, 외부 실행 방식 Guided `qm unlock`, Operation 이력·검증·복구 관찰과 로컬 계정이 있다.

CLI/TUI의 인증·조회·연결 등록과 bootstrap, CLI의 기존 VM 생성·시작·정상 종료와 작업 조회 경로는 코드로 제공하며 실제 지원 환경 검증 전이다. 템플릿 제작·일반 VM 수정과 삭제·내장 콘솔·시계열 모니터링·알림·백업과 복원·마이그레이션·일반 인프라 설정 변경은 아직 제공하지 않는다. 구현 세부사항은 [아키텍처](architecture.md)에 한 번만 기록한다.

## 6. 우선순위와 범위 제한

기능 선택 기준은 **“어떤 업무 때문에 사용자가 갈랴르를 떠나 Proxmox를 여는가?”**다. 2026-09-18 사용자가 정한 우선 목표는 기본 운영 기능을 빠르게 완성해 실제로 사용하는 것이다. 첫 버전은 **웹 + CLI**에서 업무를 끝내며, 기존 TUI는 보존하고 신규 기능 연결·UX 개선은 후속으로 둔다. 서버/API와 필요한 웹·CLI를 기능별로 함께 완성한다. 인터페이스가 달라도 같은 권한·실행 경로를 사용한다는 원칙은 유지한다. [기본 기능 로드맵](roadmap.md)은 설치·연결, VM 일상 관리, 템플릿, 모니터링, 백업·복구, 유지보수의 M1~M6로 구성한다. VM 일상 관리부터 사용을 시작하고 나머지를 추가하며 구현·인터페이스·실환경 검증 상태는 별도로 기록한다. 로드맵의 상세 첫 지원 범위는 초안이며, 제품 경계와 기능별 고위험 설계는 실행 전에 확정한다. 과거 work의 M 번호와 완료 상태는 소급 변경하지 않는다.

초기에는 모든 Proxmox 설정의 동시 구현, 자체 하이퍼바이저·백업 엔진·범용 TSDB 제작, multi-provider, 임의 shell/SSH 실행, 무승인 자동 복구를 추진하지 않는다. DRS의 자동 배치·재균형 기능은 복원하지 않는다. 향후 사용자 주도 마이그레이션은 별도 작업 계약으로 설계한다.

AI는 이후 관찰 근거 수집·작업 실패 설명·계획 제안에 활용할 수 있다. 운영 권한과 실행 검증을 모델의 판단으로 대체하지 않는다. 모든 기본 기능의 완성을 기다려야 한다는 뜻은 아니지만, 해당 업무의 관찰·실행 계약이 먼저 필요하다.

## 7. 확인할 제품 성과

첫 사용 환경에서 다음을 측정한다. 아직 측정값이나 확정된 수치 목표는 없다.

- 설치 시작부터 실제 자원 확인까지 걸린 시간과 막힌 지점
- 선택한 일상 업무를 갈랴르 안에서 완료한 비율
- Proxmox 화면으로 이동한 이유와 빈도
- 작업 결과·실패 원인·다음 조치를 파악하는 데 걸린 시간
- 미확정 결과를 성공으로 잘못 표시한 사례

## 8. 유지할 안전성과 계약

Proxmox actual state, 서버 측 권한 검사, 승인 대상과 계획의 결합, 중복 실행 방지, target lock, 기록 보존과 결과 검증을 유지한다. 미확정 변경은 무작정 재실행하지 않는다. API·DB·복구 의미와 live 작업 경계는 기존 상세 문서를 따른다.

이 PRD는 이전의 제한된 실행 목록을 장기 제품 범위로 삼던 방향을 대체한다. 이전 명세와 결정 원문은 [보관본](archive/README.md)에 남기고 유지할 결정은 [아키텍처](architecture.md)에 통합한다. 새 기능을 이미 구현했거나 live 작업을 승인했다는 뜻은 아니다.
