- 상태: 아래 제한된 첫 지원 범위·구현 순서는 사용자 승인(`2026-09-19`). live 실행·설치·운영 DB 적용은 별도 승인한다.

## 목표와 첫 사용 시점

**웹과 CLI에서 Proxmox의 기본 운영 업무를 대상 선택 → 입력·영향 확인 → 실행 → 결과 확인까지 끝낸다.** 서버/API만 구현하고 화면·명령을 나중으로 미루는 방식은 종료한다. 새 기능마다 서버와 필요한 웹·CLI를 함께 완성한다. VM 화면 콘솔은 웹에서 제공하고 CLI는 같은 웹 콘솔 진입을 안내한다. 터미널 콘솔은 첫 버전의 필수가 아니다.

M1의 실제 사용 경로를 확인하고 M2의 VM 기본 운영을 완성하면 일상 사용을 시작한다. M3~M6는 사용 중 순서대로 추가하며, 여섯 영역의 합의된 범위와 검증이 모두 끝났을 때 기본 기능 버전 완료로 선언한다. M2 완료를 전체 제품 완료로 표시하지 않는다.

속도는 지원 조합을 줄이고 기존 코드를 재사용해 확보한다. 첫 환경 하나의 OS·CPU·Docker·PVE 버전·인증 방식·storage·bridge를 먼저 기록하고 검증한다. 정확한 값은 현재 사용자 환경 확인 후 확정하며, 확인하지 않은 환경을 지원한다고 선언하지 않는다. 모든 OS·PVE·스토리지 조합 지원과 구조 전면 개편은 출시 조건에 넣지 않는다.

웹 UI는 2026-09-20 사용자 승인과 [PRD의 웹 사용 경험](prd.md#웹-사용-경험-approved)에 따라 대시보드를 포함해 전면 개선한다. 상단은 전체 현황·VM 관리·템플릿·모니터링·인프라·작업 이력으로 기능을 분리하고 계정 관리는 우측 메뉴로 옮긴다. 템플릿 제작·정리와 인프라 연결·설정·유지보수의 진입점을 모으고 모바일 탐색·VM 작업 분류를 일관되게 정리한다. 현황을 클러스터 전체와 노드 상세 탭으로 분리하고 전체 노드 집계·요약 행·노드 비교표·운영 확인 사항·최근 작업과 상세 모니터링 패널을 중심으로 정보 밀도를 높인다. 실제 화면 검토와 공통 탐색·VM 상세 구조 결정을 먼저 진행하고, 각 M2~M6 기능에 필요한 화면을 함께 완성한다. 전체 UI 교체를 기본 기능 구현의 선행 조건으로 두지 않는다.

## 현재 출발점

사용자는 2026-09-18 실제 Proxmox 연결 성공을 확인했다. 전체 환경 지원이나 mutation 권한·운영 복구 검증 완료를 뜻하지 않는다.

- 구현 기반: inventory·VM 상세·Insights, 기존 템플릿 기반 생성, 시작·정상 종료, Guided unlock, Operation 이력·검증·복구 관찰, 로컬 계정.
- 설치·연결 기반: 관리형 bootstrap과 Proxmox 등록 핵심 흐름. read/선택적 power에 M2~M5의 VM·템플릿·백업/복원 기능과 M6 정지 이동의 최소 권한·기존 연결 갱신 경로를 추가했다. OPS-03 directory storage·Linux bridge의 opt-in 권한·별도 대상 범위와 기존 연결 갱신도 추가했다.
- 인터페이스 기반: 기존 웹, [CLI 운영 흐름](work/2026-09-18-cli-workflows.md), [전체 화면 TUI](work/2026-09-18-fullscreen-tui.md). 구현·격리 검증과 실제 운영 검증은 구분한다.
- 기존 코드를 재구현하지 않는다. 부족한 권한·실행·화면·명령·검증만 채운다. TUI 기존 기능은 보존하지만 신규 기능 동등 지원과 UX 개선은 첫 버전 완료 조건에서 제외한다.

## 기본 기능 마일스톤

이 문서의 M1~M6는 **2026-09-18 기본 기능 버전의 업무 묶음**이다. 과거 work의 같은 M 번호와 범위·완료 상태가 같다는 뜻이 아니다. 기존 VM/TPL/OBS/BAK/OPS ID는 세부 기능 추적에 유지한다.

## 단계별 구현 범위와 제외 범위

### M1 — 현재 환경에서 안정적으로 시작

- 기존 설치·등록을 재사용해 웹/CLI 접속과 서버 재시작을 확인한다. 로컬 실행과 기존 서버 연결을 구분한다.
- 실제 연결의 인증 방식·권한·지원 환경과 사용할 테스트 자원을 기록한다. 관리형 권한 확장은 필요한 기능의 작업에 포함한다. 기존 연결을 몰래 env 경로로 우회하지 않는다.
- 최소 검증: 로그인/권한 거부, 연결 실패, 서비스 stop/start, bootstrap 재실행과 기존 데이터 보존. 실제 검증은 승인된 설치·대상에서 한다.
- 전체 OS/CPU/realm/MFA 조합과 공개 배포 자동화는 후속이다. 최초 사용에는 실행 가능한 이미지와 재현 가능한 설치 절차가 있어야 한다.

### M2 — VM 기본 운영을 실제로 사용

기본 순서는 권한 경로와 기존 생성·전원 흐름 보강 → VM-01 → VM-02 → VM-03 → VM-04 → VM-05 → VM-06이다. 기능 하나마다 필요한 웹·CLI와 검증까지 연결하고 다음 기능으로 이동한다.

| ID | 확정된 첫 지원 범위 | 주요 완료 조건 |
|---|---|---|
| 기존 기능 | 템플릿 기반 생성, 목록·상세, 시작·정상 종료, 작업 조회 | 선택한 관리형 연결로 실행 가능, 웹/CLI에서 같은 Operation과 결과 확인 |
| VM-01 | 정지된 VM의 CPU 코어 수·메모리 용량 변경 | 지원 필드·단위·범위 확정, 변경 전후 값 확인, 전원 상태 변경·권한 부족 차단, 부분 반영 구분 |
| VM-02 | 첫 지원 storage/bus의 디스크 확장 | 가상 디스크 실제 용량 확인, 축소 거부, 게스트 파일시스템 확장은 별도임을 안내 |
| VM-03 | 정지된 VM의 기존 NIC bridge/VLAN 변경 | 허용 필드·값 확정, 설정 재조회, 통신 영향과 게스트 연결 미검증 표시 |
| VM-04 | 정지된 VM의 full clone, 첫 지원 storage 조합 | 원본 보존, 새 VMID·설정 확인, identity/network 충돌 안내, 기본 정지 상태 유지 |
| VM-05 | 정지된 VM의 명시적 삭제 | VMID·이름·삭제 디스크/보존 자원 확인, 승인한 범위의 삭제 확인, 응답 유실 시 재삭제 금지 |
| VM-06 | 인증된 웹 콘솔 접속·종료 | 실제 화면 연결, 권한 거부·만료·종료, CLI에서 웹 진입 안내 |

실행 중 hotplug, 디스크 축소, NIC 추가·모델 변경, 자동 강제 종료, 임의 게스트 OS 변경은 첫 범위에서 제외한다. VM-01은 단일 socket의 cores(1~128)·memory MiB(128~1048576)만 지원하며 vcpus/custom NUMA topology·pending config·lock·template은 차단한다. balloon 설정은 보존한다. 복제·삭제의 잔여 자원과 복구 불가 영향은 구현 work에 명시한다.

### M3 — 템플릿 준비부터 배포 확인

- TPL-01: 준비된 VM의 템플릿 전환. 원본 영향과 계정·키·머신 식별 정보 준비 조건을 확인한다.
- TPL-02: 공식 cloud image 한 OS/버전으로 제작. 출처·무결성 확인, PVE 실행 경로, 실패 잔여 자원을 정한다. 임의 SSH/shell executor를 기본 해법으로 도입하지 않는다.
- TPL-03: 기존 생성 흐름으로 테스트 VM을 배포해 부팅·cloud-init·네트워크·접속·guest agent 결과를 각각 기록하고 명시적으로 정리한다. 자동 테스트 자원 삭제도 승인된 범위를 따른다.
- VM 생성 기반과 테스트 자원 정리 경로가 필요하다. TPL-03은 기존 템플릿으로 먼저 검증할 수 있다.
- ISO 무인 설치, 모든 OS 지원, 기존 VM의 자동 OS 업데이트는 제외한다.

### M4 — 현재 상태와 이력 확인

- OBS-01: 노드·VM·storage의 지원 지표, 관찰 시점과 누락을 표시한다.
- OBS-02: PVE 제공 이력을 우선 사용해 추이를 조회한다. 제공 기간·해상도·지표는 실제 환경 확인 후 계약으로 고정한다.
- OBS-03: 기본 임계 상태와 작업 실패의 발생/해제·이력을 제품 안에서 확인한다. 임계값·중복 처리·보존 기준을 구현 work에서 정한다.
- 웹은 요약·추이와 상세 진입, CLI는 같은 지표·이력의 조회를 제공한다. 화면 모양의 동일성은 요구하지 않는다.
- 단절을 0/정상으로 표시하지 않는다. 자체 범용 TSDB·APM·외부 알림 발송·자동 복구는 제외한다. collector나 scheduler가 필요하면 도입 전 범위·검증·복구를 정한다.

### M5 — 백업과 별도 VM 복원

- BAK-01: 첫 지원 PVE backup storage의 목록·시점 조회와 명시적 백업 실행. 공간 부족·실패와 실제 완료를 구분한다.
- BAK-02: 선택 백업을 새 VMID로 복원한다. 원본·백업을 보존하고 부팅과 정의된 검사 결과를 각각 표시한다. 네트워크 충돌 방지 방식을 먼저 정한다.
- VM 생성·전원·작업 추적을 재사용한다. 모니터링 전체 완료를 기술적 선행 조건으로 삼지 않는다.
- 클라이언트 종료·연결 단절·서버 재시작 후에도 결과를 조회할 수 있어야 한다. 결과 불명 시 자동 재실행하지 않는다.
- 전체 PBS 관리, 원본 덮어쓰기, 자동 백업 삭제·보존 정책 변경, 자동 재해 복구는 제외한다.

### M6 — 제한된 유지보수

- OPS-01: 첫 지원 storage/network 조합의 정지 VM 수동 노드 이동. 대상 호환성·영향 확인, 실행 후 위치·전원 상태와 미확정 결과를 기록한다.

## Goal 실행 규칙과 완료 기준

2026-09-23 현재 checkout(`712ff12`)의 공통 로컬·컨테이너 검증과 별도 PostgreSQL 17 통합 검사 78개를 재실행해 통과했다. Client 257개, Backend 1,645개 및 Frontend test/lint/build를 확인했으며 Node 24 Frontend와 컨테이너 Client도 캐시와 별개로 다시 실행했다. [최신 검증 기록](work/2026-09-19-basic-features.md#자동-회귀-재검증-2026-09-23)을 따른다. 이번 검사는 실환경 mutation·설치·브라우저 검증을 포함하지 않으며 아래 M1~M6 실사용 잔여 항목은 유지한다.

마일스톤은 업무 묶음이고 Goal은 그 안의 검증 가능한 실행 목표다. 같은 업무를 끝내기 위한 서버·웹·CLI 변경은 한 Goal에 포함할 수 있다. 첫 버전 전체를 한 Goal로 실행하려면 아래 범위·순서와 단계별 종료 조건을 먼저 확정한다. 미정 지원 범위를 임의로 확대하지 않는다.

각 실행 work에는 사용자 결과, 지원/제외 범위, 필요한 권한·API·잠금·복구 계약, 구현 순서, 자동 검증, 실환경 대상/영향, 실패 시 확인·복구 방법을 함께 기록한다. 후속 기능의 상세 work를 미리 모두 만들지 않는다.

1. **구현 검증 완료:** 서버 + 해당 웹/CLI 흐름과 필요한 테스트 완료. 입력 오류·권한 거부·상태 변경·중복 요청·부분 실패·결과 미확정을 검증한다. 기존 target lock·idempotency·Operation·GET-only 복구 계약을 유지한다.
2. **실사용 검증 완료:** 승인된 지원 환경과 정확한 대상에서 사용자 흐름·실제 결과·오류 안내를 확인하고 근거를 연결한다. API 접수나 task 발급만으로 완료 처리하지 않는다.
3. **기능 완료:** 위 두 조건을 만족하고 사용법·알려진 제한·상태표를 갱신한다. 서버만 끝난 기능은 완료로 표시하지 않는다.
4. **기본 기능 버전 완료:** 확정한 M1~M6 범위를 모두 만족하고, 전체 회귀 검증 및 재현 가능한 설치/실행 절차를 확인한다. TUI 개선과 후속 범위는 포함하지 않는다.

검증 명령은 [개발·운영 안내](development.md)의 단일 기준을 따른다. 변경 범위별 검사와 `git diff --check`, 공통 `pnpm run verify`, 기준 `pnpm run verify:container` 결과를 구분해 기록한다. 미실행 검증은 이유와 함께 남긴다.

live mutation은 정확한 대상·영향에 대한 별도 승인 뒤 실행한다. 승인 대기 중에는 실환경 검증을 미완료로 남기고, 그 결과에 의존하지 않는 승인 범위의 구현·자동 검증은 계속할 수 있다. 승인이나 지원 범위 결정 없이는 진행할 수 없는 작업은 구체적인 차단 이유를 보고한다. 코드 작성 Goal의 종료와 제품 기능 완료를 혼동하지 않는다.

DB·인증·권한·잠금·복구 등 고위험 변경은 [AGENTS.md](../AGENTS.md)에 따라 범위·검증·복구를 먼저 work에 정한다. 문서 정리는 실제 구현·배포·live mutation의 포괄 승인이 아니다. 커밋·푸시는 사용자 요청이 있을 때만 한다.

## 다음 실행 준비

1. 현재 work의 최신 재개 지점과 요구사항별 검증표를 대조한다. M2~M6 구현을 다시 시작하지 않고 통합 검증에서 발견한 결함을 수정한다.
2. 승인된 macOS arm64/local Docker 전용 설치에서 bootstrap 중단 후 동일 경로 재개, 실제 웹/CLI 로그인, stop/start·동일 경로 재실행과 데이터/secret 보존을 확인했다. 첫 시도 Docker 오류 원인은 미확정이며 중단 없는 신규 설치·다른 OS 지원 완료로 확대하지 않는다. VM 상세 작업/진단 접기, 사용량 화면의 미관찰 정보량·모바일 차트, Proxmox 등록 이력/새 등록 분리와 권한 그룹을 실제 설치 화면에서 정리했다. 브라우저 fixture로 백업→복원→검사 보고서의 모바일 흐름을 확인하고 유지보수→이동 화면의 목적 노드 전달 누락을 수정했다. 실제 복원·이동 검증은 별도로 남긴다. 생성 검토 요약은 모바일 두 열로 정리하고, 격리 browser로 지정 템플릿·입력 보존·검토 승인/최종 실행 동의 분리를 확인했다. 실제 기능 실행 뒤 결과 화면과 남은 관리형 연결 검증은 계속한다.
3. 제공된 CA의 제품 TLS 호환 수정과 실제 token import가 완료됐다. 관리형 source 재시작 후 웹·CLI에서 7001을 조회·변경했다. 이후 필요한 기능은 기존 token 권한과 제품의 선택 범위를 대조해 기존 연결 갱신 경로로 준비한다. insecure 우회나 임의 DB credential 주입은 하지 않는다.
4. 7001의 정상 종료·웹 4→2 cores/8192→4096 MiB·CLI 원복·재시작을 확인했다. native power 응답을 읽지 못하던 CLI 결함도 수정했다. 7001 삭제는 허용됐으나 아직 실행하지 않았고 다른 기존 VM으로 확대하지 않는다. 다음은 나머지 M2~M6이며 새 테스트 VMID 40000~40010은 실행 직전 점유를 확인한다. 아직 승인되지 않은 정확한 대상·부작용·정리 범위는 실행 전에 구체화한다.
5. 사용자는 2026-09-19 신규 PVE 로그인·OTP·전용 token 발급/권한 설정과 최초 등록 흐름 검증을 기능 검증·UI 정리 뒤로 미뤘다. 기존 token 사용 성공으로 이 경로를 완료 처리하지 않으며, 마지막에 제품 비밀 입력 화면에서 사용자와 확인한다. 전체 Goal 완료 조건에서 제거하지 않는다.

## 후속 범위와 과거 기록

TUI 신규 기능·UX 개선, 지원 OS/PVE/storage 조합 확대, 공개 release 자동화, 키 rotation·이전 연결 source 복귀·불명 발급 수동 종료의 운영 도구 보강은 별도로 관리한다. 첫 환경에서 필수인 복구 절차는 후속으로 미루지 않고 M1 또는 해당 기능에 포함한다.

기업용 조직·쿼터·SSO, 다중 클러스터, AI와 자동 DRS는 첫 버전 완료 조건에 추가하지 않는다.

과거 work의 M 번호와 완료 기록은 수정하지 않는다. [원본 묶음](archive/README.md)의 `project-docs/archive/plans/2026-09-14-remaining-work-closure.md` B·C에 남은 VM 101·900 진단, 템플릿 3000 guest-exec 정책, production 배포·Git 정리는 당시 대상이다. 새 기능의 완료 근거로 사용하지 않으며 실행 전 현재 대상·접근·영향을 재확인한다.
