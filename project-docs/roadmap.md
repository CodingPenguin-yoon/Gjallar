# Gjallar 마일스톤 로드맵

- 갱신일: `2026-09-17`
- 기준: [PRD](prd.md)의 제품 목표와 [아키텍처](architecture.md)의 현재 구현
- 상태: M1-1·M1-2 구현, M1-3·M1-4의 credential 저장·등록 핵심 흐름 구현과 격리 검증 완료. 실제 설치·Proxmox 9.0.11 연동 및 복구 지원 검증이 남아 전체 M1은 진행 중이다.

## 현재 위치와 진행 순서

현재 웹에는 inventory·VM 상세·Insights, 기존 템플릿 복제 기반 생성, 시작·정상 종료, Guided unlock, 작업 이력·검증·복구 관찰과 로컬 계정이 있다. 이 기반을 재사용하되 아래 마일스톤을 완료한 것으로 간주하지 않는다.

| 단계 | 사용자가 얻는 것 | 선행 조건 | 현재 상태 |
|---|---|---|---|
| M1. 설치·연결 | 로컬 Gjallar 실행 또는 기존 서버 접속으로 첫 자원 확인 | 시작 방식 합의, 잔여 구현 승인 | M1-3·M1-4 핵심 구현 · M1-5 실환경 검증 대기 · 전체 진행 중 |
| M2. VM 일상 관리 | VM 생성부터 설정 변경·콘솔·삭제까지 처리 | M1의 연결·권한·CLI 기반 | 미착수 · 기존 생성/전원 기능 활용 |
| M3. 템플릿 관리 | 템플릿 준비·제작·검증에서 VM 배포까지 연결 | M2의 VM 관리·작업 검증 | 미착수 · 기존 템플릿 조회 활용 |
| M4. 모니터링 | 상태·사용량·추이·문제를 확인하고 조치로 이동 | M1의 관찰 truth, M2의 대상·작업 연결 | 미착수 · 기존 inventory/Insights 활용 |
| M5. 백업·복구 | 백업을 만들고 별도 VM으로 복원해 확인 | M2의 VM/작업 관리, M4의 상태 확인 | 미착수 |
| M6. 인프라 유지보수 | VM 이동과 필요한 노드·스토리지·네트워크 업무 처리 | M2·M4·M5의 실행·관찰·복구 기반 | 미착수 |

기본 순서는 M1 → M2 → M3 → M4 → M5 → M6다. 선행 조건은 기술적 의존성이며 모든 앞 단계의 완성이 필요한 것은 아니다. 예를 들어 M4는 M3 제작 기능 자체에 의존하지 않는다. 순서를 바꾸면 이유와 영향을 이 문서에 반영한다. 일정·예상 기간은 첫 구현 범위와 검증 환경을 확인한 뒤 정한다.

## 모든 단계의 완료 기준

- 지원하는 환경·대상·기능과 제외 범위를 명시하고, 사용자가 대상 확인 → 실행 → 결과 확인까지 갈랴르에서 완료한다.
- 조회 실패·stale/unknown·작업 진행·성공·실패·확인 불가를 구분한다. API 접수만으로 성공을 표시하지 않는다.
- 변경 작업은 서버 측 권한·사전 검사·중복 방지·계획 결합·기록·결과 검증을 적용한다. 미확정 mutation을 무작정 재시도하지 않는다.
- 정상 경로뿐 아니라 권한 부족·연결 실패·중복 요청·해당 작업의 중단/부분 실패를 검증하고 결과를 work에 남긴다.
- 웹과 CLI의 같은 작업은 같은 API·권한·Operation을 사용한다. 코드 반영·검증·운영 배포는 구분하고, 검증하지 못한 지원 환경은 완료로 표시하지 않는다.

CLI는 M1에서 인증·연결·조회와 구조화된 출력·종료 코드의 기반을 만들고, M2부터 각 단계의 작업을 함께 제공한다. VM 화면은 웹 콘솔을 사용하며 CLI는 같은 대상의 콘솔 진입을 지원하는 방식으로 설계한다. 별도의 터미널 화면 프로토콜까지 동일하게 구현한다는 뜻은 아니다.

## M1. 설치·연결

**목표:** 개발자가 환경을 대신 구성하지 않아도 사용자가 갈랴르를 시작하고 자신의 Proxmox 자원을 확인한다.

- **포함:** macOS·Linux 지원 환경과 의존성 정의, 로컬 Gjallar 실행/기존 서버 연결을 선택하는 bootstrap, 최초 계정, Proxmox 로그인 후 권한을 확인한 전용 토큰 발급·보관, 인증서·권한·연결 진단, 웹·CLI·TUI의 인증·첫 조회 기반.
- **제외:** Proxmox 자체 설치, 다중 클러스터, 클라이언트의 Proxmox 직접 연결 운영 모드, 기업 SSO, 완전한 무의존 단일 바이너리 제공 약속. 전체 VM 관리 TUI와 MCP는 M1에 포함하지 않는다.
- **합의한 방향:** [PRD의 설치·접속 경험](prd.md)을 따른다. 로컬·원격 모두 같은 Gjallar API를 사용하며 토큰·작업 기록은 서버가 관리한다.
- **현재 구현:** M1-1은 Python CLI/메뉴 TUI·cookie session·keyring/memory·기본 조회, M1-2는 Compose·최초 관리자·명시적 init/serve·서비스 관리다. M1-3·M1-4는 암호화 token 저장·env import·서버 PVE 로그인/TOTP·scope 계획·발급/ACL·검증·전환·명시적 폐기와 웹/CLI/TUI 등록 흐름이다. 새 관리형 profile은 read/선택적 power만 지원한다. 명령은 [개발 안내](development.md), 근거는 [M1 작업 기록](work/2026-09-16-m1-installation-connection.md)에 둔다.
- **남은 선행 조건:** macOS/Linux 설치·OS keyring·실제 PVE package/realm/MFA/TLS 및 기존 DB 전환 검증, 공개 release artifact/patch 고정. 사용자 제공 PVE 버전은 9.0.11이며 아직 live 검증 증거는 없다. 키 rotation·이전 source 복귀·불명 발급 수동 종료의 운영 절차/지원 범위도 남아 있다. PostgreSQL 17 격리 동시성은 통과했다. live 설치·migration·token/ACL 변경은 별도 대상·영향 승인 후 진행한다.
- **완료 기준:**
  1. 지원 대상으로 선언한 macOS·Linux 환경에서 문서화된 설치 → 계정 생성 → 연결 → 실제 자원 조회를 재현한다.
  2. 웹과 CLI가 같은 연결 대상과 권한 범위의 자원을 보여준다.
  3. 인증 실패·TLS 문제·권한 부족·연결 불가를 구분하고 복구할 설정을 안내한다. secret을 로그·출력에 노출하지 않는다.
  4. bootstrap 재실행과 서비스 재시작이 기존 설정·데이터를 의도치 않게 덮어쓰지 않는다. 중간 실패 후 다음 행동을 안내한다.
  5. 로컬 실행은 서비스·DB 준비부터 첫 조회까지, 기존 서버 연결은 클라이언트 준비·Gjallar 로그인부터 첫 조회까지 재현한다. 기존 서버 연결 경로는 로컬 DB·Proxmox 토큰을 요구하지 않는다.
  6. 새 Proxmox 연결은 권한 확인·전용 토큰 발급·안전한 저장·토큰 조회 검증을 마친 뒤에만 완료로 표시한다. 비밀번호 비보관, 발급/저장 중단, 중복 실행, 토큰 권한 변경·폐기 시나리오를 검증한다.
  7. TUI 종료가 서비스를 암묵적으로 종료하거나 토큰을 폐기하지 않는다. 다음 실행의 연결 선택을 보존하고 현재 접속 서버를 명확히 표시한다.
- **상태:** M1-1·M1-2 구현, M1-3·M1-4 핵심 코드·격리 검증 완료. M1-5 실제 설치·PVE 등록/첫 조회/중단 복구와 위 운영 공백의 검증이 남아 **전체 M1은 미완료**다. 초기 진단 우선안은 `SUPERSEDED`다.

## M2. VM 일상 관리

**목표:** 일상적인 VM 업무를 위해 Proxmox 화면으로 이동하지 않는다.

- **포함:** 기존 VM 상세, 기존 템플릿 기반 생성, 지원되는 VM 복제, 시작·정상 종료, CPU/RAM 변경, 디스크 확장, NIC 변경, 명시적 삭제, 웹 콘솔 접속과 CLI의 같은 운영 작업.
- **제외:** 디스크 축소, 임의 게스트 OS 설정, ISO 설치 자동화, 마이그레이션, 자동 강제 종료, 모든 장치 종류 지원.
- **선행 결정:** M1의 연결·권한·CLI 계약. 기능별 지원 VM/스토리지 조건, 재시작 필요 여부, 삭제할 디스크 범위, 콘솔 인증·세션 수명.
- **완료 기준:**
  1. 지원 VM을 생성·복제하고 사양/디스크/NIC를 변경한 뒤 실제 결과를 조회한다. 기존 VM도 동일한 관리 흐름을 사용한다.
  2. 중단이 필요한 변경은 실행 전 표시한다. 가상 디스크 확장과 게스트 파일시스템 확장을 구분한다.
  3. 콘솔은 권한 있는 사용자만 접속하며 세션 만료·종료가 동작한다. 삭제는 정확한 대상·관련 디스크·복구 불가 영향을 확인한 뒤 수행하고 결과를 검증한다.
  4. CLI에서 시작한 작업을 웹의 같은 Operation으로 확인한다. 클라이언트 종료·재요청이 중복 mutation을 만들지 않고 서버에서 작업 결과를 확인할 수 있다.
- **상태:** 미착수. 기존 생성·시작·정상 종료와 작업 기반을 재사용한다. 기능별 작은 구현 묶음으로 진행한다.

## M3. 템플릿 관리

**목표:** 템플릿을 준비하는 단계부터 해당 템플릿으로 VM을 배포하는 단계까지 연결한다.

- **포함:** 기존 템플릿 발견·선택/등록·상세 관리, 준비된 VM의 템플릿 전환, 지원하는 공식 클라우드 이미지 기반 제작, 배포 준비 검사와 검증 결과 표시.
- **제외:** 모든 OS의 ISO 무인 설치, 기업 카탈로그·승인 체계, 기존 VM의 자동 OS 업그레이드, 범용 이미지 빌드 플랫폼.
- **선행 결정:** M2의 VM 작업·검증 경로, 최초 지원 이미지/버전·출처 검증, 원본 VM 전환 영향, 계정·키·머신 식별 정보 처리, 검증 VM 생성·격리·정리 방식.
- **완료 기준:**
  1. 지원 경로로 템플릿을 준비·제작한 뒤 갈랴르에서 VM을 생성한다.
  2. 테스트 VM으로 부팅·cloud-init·네트워크·접속·필요한 guest agent 조건을 검사하고 완료·실패·확인 불가를 구분한다.
  3. 테스트 자원과 실패한 제작의 잔여 자원을 표시하고 명시된 정리 절차를 제공한다.
  4. OS·설정 기반인 템플릿과 사양 프리셋을 구분한다. 제작/검사 이력을 웹·CLI에서 확인하며 템플릿 변경이 기존 VM 자동 변경으로 오해되지 않게 한다.
- **상태:** 미착수. 기존 템플릿 조회·복제는 이미 있으나 제작과 검증 절차는 새로 필요하다.

## M4. 모니터링

**목표:** 무엇이 정상이고 무엇을 확인해야 하는지 파악한 뒤 관련 관리 작업으로 이동한다.

- **포함:** 노드·VM·스토리지 상태, CPU·메모리·용량·디스크/네트워크 활동의 지원 지표와 추이, 작업 실패, 관찰 시점·누락 표시, 기본 임계 상태와 알림 이력.
- **제외:** 자체 범용 TSDB, APM·게스트 내부 전체 모니터링, 자동 복구, 모든 외부 알림 채널. 초기 알림은 갈랴르 안에서 조회하는 범위이며 외부 발송은 후속으로 둔다.
- **선행 결정:** M1의 연결 truth와 M2의 대상/작업 연결. 지표별 실제 수집 가능 여부·source·주기·보존 기간·임계값·반복 알림 처리. 기존 Proxmox 지표 활용과 추가 저장 필요성을 먼저 검토한다.
- **완료 기준:**
  1. 지원 지표의 현재 값·관찰 시점·정해진 기간의 추이를 확인한다. 수집 주기와 보존 정책을 문서화하고 검증한다.
  2. 연결 단절·수집 누락을 사용량 0이나 정상으로 표시하지 않는다. VM 실행 상태와 애플리케이션 건강 상태를 구분한다.
  3. 임계 상태 발생·해제와 작업 실패를 재현하고, 반복 관찰이 무제한 중복 알림을 만들지 않는다.
  4. 웹·CLI에서 같은 상태/알림을 확인하고 관련 VM·작업 상세로 연결한다.
- **상태:** 미착수. 현재 inventory·Insights의 관찰 기능은 유지하고 시계열·알림을 추가한다.

## M5. 백업·복구

**목표:** 백업의 존재뿐 아니라 실제 복원 결과까지 갈랴르에서 확인한다.

- **포함:** 지원 백업 대상의 목록·시점·작업 상태 조회, 백업 실행, 별도 VM으로 복원, 복원 후 상태와 정의된 검사 결과 확인, CLI·웹 공통 작업 이력.
- **제외:** 자체 백업 엔진, 기존 VM 자동 덮어쓰기, 자동 재해 복구·서비스 전환, 모든 PBS 관리 기능, 백업 자동 삭제/보존 정책 변경.
- **선행 결정:** M2의 VM/작업 관리와 M4의 상태 확인. 지원 PVE 백업 경로·PBS 연동 범위, 권한·스토리지·복원 VMID·네트워크 격리·검증 기준. 모든 서비스의 복구를 보장하지 않는다.
- **완료 기준:**
  1. 백업 실행 → 완료 확인 → 선택한 백업을 새 VM으로 복원 → 부팅/정의된 검사 결과 확인을 재현한다.
  2. 원본 VM·백업을 의도치 않게 변경하지 않고 대상 ID 충돌·공간 부족·복원 실패를 명확하게 처리한다.
  3. 긴 작업의 연결 단절·클라이언트 종료·서버 재시작 후 상태를 확인한다. 부분 실패를 전체 성공으로 표시하거나 같은 복원을 무작정 재실행하지 않는다.
  4. 백업 완료·VM 복원 완료·서비스 확인 완료를 분리하고 미검증 항목을 표시한다.
- **상태:** 미착수. 현재 GET-only 작업 복구는 백업 복원 기능을 의미하지 않는다.

## M6. 인프라 유지보수

**목표:** 지원하는 인프라 유지보수를 영향 확인부터 결과 검증까지 처리한다.

- **포함:** 사용자 주도 VM 마이그레이션, 노드 유지보수 준비·대상 VM/자원 확인, 업무에 필요한 제한된 스토리지·네트워크 설정 변경과 CLI 지원.
- **제외:** 자동 DRS, 다중 클러스터 이동, Ceph 전체 관리, 클러스터 설치·재구성, 임의 호스트 shell, 모든 네트워크 설정 지원.
- **선행 결정:** M2·M4·M5의 실행·관찰·복구 기반. 지원 migration 모드·storage/network 호환 조건·중단 가능성, 허용할 설정 변경 목록, 관리 연결 상실 시 복구 경로. 목록과 복구 절차가 정해지기 전 mutation을 구현하지 않는다.
- **완료 기준:**
  1. 지원 VM의 이동 가능 여부와 불가 사유를 확인하고 명시적 실행 후 실제 위치·전원 상태를 검증한다.
  2. 노드 유지보수 계획에서 영향을 받는 VM과 중단 가능성을 표시한다. 대상 하나의 실패 시 완료·미완료를 구분하고 정의된 지점에서 중단한다.
  3. 범위로 확정한 스토리지·네트워크 변경을 웹·CLI에서 수행하고 결과를 확인한다. 관리 연결 상실 등 실패 시 사용할 별도 복구 절차를 검증한다.
  4. 일반 운영은 갈랴르에서 완료하되 Proxmox의 비상 관리 경로는 유지한다.
- **상태:** 미착수. 착수 시 지원 변경 목록을 이 절에 구체화한다.

## 상태와 문서 관리

- 상태는 미착수 → 설계 중 → 구현 중 → 검증 중 → 완료로 갱신한다. 일부 기반이 있다고 마일스톤 전체를 완료로 표시하지 않는다.
- 완료 시 work의 실제 검증 결과를 연결한다. 기능 목록·기한만으로 완료를 선언하지 않는다.
- 큰 작업은 [work](work/README.md)의 한 문서에 범위·계획·결과·검증·남은 일을 이어 기록한다. 현재 계약이 바뀌면 아키텍처·개발 안내도 갱신한다.
- 이번 문서는 제품 단계와 완료 기준이다. 고위험 구현의 구체적 설계와 live mutation 승인은 [AGENTS.md](../AGENTS.md)의 경계를 따른다. 현재 코드·DB·배포 상태는 바꾸지 않는다.
