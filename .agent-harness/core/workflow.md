# 작업 흐름과 위험도 정책

이 문서는 신규 설계부터 일반 구현, 고위험 작업, 완료 보고까지의 공통 절차를 정의한다.

## 대화 원칙

설계 결정에 사용자 입력이 필요하면 한 번에 하나의 의미 있는 질문만 한다. 질문마다 다음을 함께 제공한다.

- 현재 확인된 사실
- 추천안
- 추천 이유와 감수할 단점
- 사용자의 결정이 바꾸는 범위

현실적인 선택지는 적합도 순으로 최대 세 개까지만 제시한다. 명백한 추천안이 하나뿐이면 억지로 선택지를 늘리지 않는다.

프로젝트 설계처럼 여러 결정을 순서대로 묻는 대화에서는 현재 단계와 남은 핵심 질문의 예상 개수를 짧게 표시한다. 사용자의 답에 따라 질문 수가 달라질 수 있으면 그 사실도 함께 알린다.

## 공통 작업 생명주기

```text
요구사항 확인
→ 기존 구조와 현재 동작 조사
→ 목표·범위·완료 조건 확정
→ 위험도 분류
→ 필요한 승인 또는 Plan
→ 구현과 테스트
→ 검증 및 diff 검토
→ 관련 문서 동기화
→ 결과와 위험 보고
```

## 요구사항 정리

구현 전에 다음을 구분한다.

- 현재 동작: 코드와 테스트로 확인한 사실
- 목표 동작: 사용자가 관찰할 수 있는 변경 결과
- 범위: 이번 작업에 포함되는 책임
- 비범위: 의도적으로 변경하지 않는 항목
- 완료 조건: 검증 가능한 인수 조건
- 제약: 호환성, 데이터, 보안, 성능, 일정 조건
- 미확정: 구현 전에 사용자 결정이 필요한 항목

## 위험도 분류

### 고위험 확정 조건

다음 중 하나라도 해당하면 고위험으로 분류한다.

- DB 스키마, migration, 데이터 소유권, 트랜잭션 또는 정합성 변경
- 인증, 권한, 개인정보, 시크릿 처리 변경
- 외부 소비자가 의존하는 공개 계약의 호환성 변경
- 새로운 외부 시스템, 메시지, 캐시, 스케줄러 또는 운영 의존성
- 도메인 경계, 의존성 방향, 주요 기술 또는 아키텍처 변경
- 동기 처리를 비동기·이벤트 방식으로 변경
- 동시성, 재시도, 멱등성, 보상 처리 도입 또는 변경
- 실패 시 데이터 손실, 중복 처리, 광범위한 장애 가능성
- 되돌리기 어려운 데이터 변환이나 대규모 레거시 분해

### 불확실성 상승 조건

다음 항목은 하나만으로 항상 고위험은 아니지만 여러 개가 겹치면 고위험으로 올린다.

- 여러 도메인이나 주요 모듈에 영향
- 현재 동작을 보호하는 테스트가 부족함
- 요구사항이나 완료 조건이 불명확함
- 상태 전이와 실패 흐름이 복잡함
- 영향받는 외부 소비자를 정확히 알 수 없음
- 롤백 방법이 불분명함

불확실한 경우 먼저 조사해 위험도를 낮춘다. 조사 후에도 핵심 영향이 확인되지 않으면 고위험으로 취급한다.

### 일반 작업 조건

다음을 모두 만족하면 일반 작업으로 본다.

- 승인된 아키텍처와 기존 패턴 안의 변경
- 영향이 특정 기능이나 모듈에 국한됨
- 공개 계약과 데이터 구조를 바꾸지 않음
- 쉽게 되돌릴 수 있음
- 관련 테스트가 존재하거나 작성 가능함
- 실패 영향이 제한적임
- 보안·권한·외부 시스템 변경이 없음

파일 개수나 코드 줄 수만으로 위험도를 결정하지 않는다.

## 위험도 보고 형식

작업 시작 시 필요한 경우 다음처럼 짧게 보고한다.

```text
위험도: HIGH
근거: DB migration, 외부 API 소비자 영향
필요 절차: 공유 Plan, 사용자 승인, 구현 후 독립 리뷰
```

일반 작업은 판단 근거를 한 문장으로 설명하고 바로 진행할 수 있다.

## 고위험 작업

고위험 작업은 다음을 수행한다. 기간이 길거나 단계가 많다는 사실만으로 공유 Plan을 강제하지 않으며, 일반 작업의 실행 계획은 로컬 계획으로 관리한다.

1. `$task-planning`을 사용해 현재 상태와 영향 범위를 조사한다.
2. `project-docs/plans/`에 공유 Plan을 `DRAFT`로 작성한다.
3. 중요한 선택지, 추천안, 롤백·복구 방향을 사용자에게 제시한다.
4. 승인 내용을 Plan과 필요 시 ADR에 기록한다.
5. 작은 수직 단계로 구현하고 각 단계에서 검증한다.
6. 완료 전에 `$quality-review`로 독립 리뷰한다.
7. 실제 결과에 맞게 현재 상태 문서를 동기화한다.

## 일반 작업

일반 기능, 명확한 버그 수정, 호환 가능한 내부 리팩터링은 공유 Plan 없이 진행한다.

1. 관련 코드와 테스트를 확인한다.
2. 필요한 경우 로컬 계획을 사용하되 `.agent-local/`에만 둔다.
3. 가장 작은 일관된 변경을 구현한다.
4. 관련 검증을 실행한다.
5. 공동 문서에 실제 영향이 있는지 확인한다.
6. 최종 diff와 남은 위험을 보고한다.

## 승인 경계

반드시 사용자 승인을 받는 항목:

- 최초 기술 스택, 주요 버전, 아키텍처, 주요 도메인
- 데이터 소유권과 트랜잭션 경계
- 호환성을 깨는 공개 계약
- 파괴적 DB 변경과 대규모 데이터 이동
- 인증·권한·보안 구조
- 새로운 운영 의존성이나 외부 시스템
- 기존 프로젝트의 아키텍처 전환

반복 승인이 필요하지 않은 항목:

- 승인된 구조 안의 일반 구현
- 테스트 추가와 버그 수정
- 공개 계약을 유지하는 내부 리팩터링
- 프로젝트가 이미 선택한 도구를 이용한 검증
- 실제 변경에 따른 문서 동기화

## 상태와 승인

- 신규 프로젝트 명세와 아키텍처는 `DRAFT`에서 시작한다.
- 사용자가 핵심 결정을 확인한 뒤 `APPROVED`로 바꾼다.
- `DRAFT`인 신규 프로젝트는 첫 구현을 시작하지 않는다.
- 기존 프로젝트는 문서가 완전하지 않다는 이유로 긴급 유지보수를 막지 않는다.
- 중요한 결정이 바뀌면 기존 ADR을 덮어쓰지 않고 새 ADR로 대체 관계를 기록한다.

## 완료 흐름

일반 변경은 다음을 확인한다.

```text
요구사항 재확인
→ 최종 diff 검토
→ 테스트·Lint·타입·빌드
→ 문서 영향 확인
→ 결과와 미검증 위험 보고
```

고위험 변경은 여기에 독립 리뷰, 발견 문제 수정, 재검증을 추가한다.
