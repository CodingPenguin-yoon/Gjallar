# 테스트와 검증 원칙

이 문서는 구현 결과를 프로젝트의 실제 환경에서 검증하고 정확하게 보고하는 기준을 정의한다.

## 기본 원칙

- Project Profile에 기록된 환경과 명령을 사용한다.
- 변경 영역과 위험에 비례해 검증한다.
- 실제로 실행하지 않은 명령을 성공으로 보고하지 않는다.
- 실패를 숨기기 위해 테스트, 타입, Lint 규칙을 약화하지 않는다.
- 커스텀 범용 검사기보다 프로젝트 생태계의 공식 도구를 우선한다.

## 환경

- FastAPI 같은 Python 프로젝트는 프로젝트가 선택한 로컬 가상환경과 lock 파일을 사용한다.
- Spring Boot 프로젝트는 승인된 JDK와 build wrapper 또는 프로젝트가 선택한 재현 가능한 도구를 사용한다.
- React 프로젝트는 승인된 Node 버전, 패키지 관리자, lock 파일을 사용한다.
- 전역 도구로 우회하지 않고 프로젝트 명령을 실행한다.
- 환경 구성이 불완전하면 임의로 다른 도구를 섞지 않고 필요한 결정을 사용자에게 제시한다.

## 테스트 전략

### 버그 수정

1. 가능하면 실패를 재현하는 테스트를 먼저 추가하거나 식별한다.
2. 수정 전 실패 원인이 기대한 원인과 일치하는지 확인한다.
3. 증상이 아니라 근본 원인을 수정한다.
4. 회귀 테스트와 관련 테스트를 실행한다.

### 기능 추가

- 정상 흐름, 경계값, 실패 흐름을 검증한다.
- 권한과 데이터 소유권이 중요하면 별도로 검증한다.
- API, DB, 외부 시스템 경계는 통합 또는 계약 테스트를 고려한다.
- 핵심 비즈니스 규칙은 외부 기술 없이 빠르게 테스트할 수 있게 한다.

### 리팩터링과 레거시

- 외부 동작을 바꾸지 않는 리팩터링은 기존 테스트로 동작을 보호한다.
- 테스트가 부족한 레거시는 characterization test를 먼저 추가한다.
- 테스트를 만들 수 없는 영역은 이유와 수동 검증, 남은 위험을 기록한다.

오탈자, 문서, 외부 동작이 없는 단순 설정에는 의미 없는 테스트를 생성하지 않는다. 고정된 커버리지 수치보다 중요한 경로와 실패 조건을 우선한다.

## 검사 선택

변경 영역에 맞는 항목을 선택한다.

- Formatter 또는 포맷 검사
- Lint
- 타입 검사
- 단위 테스트
- 통합·계약 테스트
- 빌드
- 필요한 경우 로컬 실행 또는 수동 확인

명령은 Project Profile의 검증 표를 따른다. Profile에 명령이 없으면 기존 설정과 스크립트를 조사하고 사용자와 확정해 기록한다.

## 완료 전 diff 검토

- 요구사항과 인수 조건 누락
- 계획과 실제 구현 차이
- 공개 계약과 데이터 정합성 회귀
- 책임 집중, 도메인 침범, 불필요한 추상화
- silent failure, broad catch, 무제한 재시도
- 보안과 시크릿 노출
- 테스트 삭제·skip·약화
- 범위 밖 변경, 디버깅 코드, 임시 파일
- 공동 문서 동기화 누락 또는 불필요한 문서 변경

## 독립 리뷰

고위험 작업 또는 사용자가 명시한 리뷰는 `$quality-review`를 사용한다. 리뷰는 구현자의 의도를 옹호하지 않고 요구사항과 실제 diff를 기준으로 결함을 찾는다.

리뷰에서 문제가 발견되면 구현 흐름으로 돌아가 수정하고 관련 검증을 다시 실행한다. 리뷰 Skill 자체는 사용자가 수정을 요청하지 않은 한 파일을 변경하지 않는다.

## 결과 보고

검증 항목마다 다음 중 하나를 사용한다.

- 성공: 명령을 실행했고 종료 상태와 결과를 확인함
- 실패: 명령이 실패했으며 원인과 영향을 확인함
- 미실행: 실행하지 못했거나 범위에 필요하지 않음

최종 보고에는 다음을 포함한다.

1. 구현 결과
2. 주요 설계 결정과 변경 파일 역할
3. 실행한 검증 명령과 결과
4. 갱신한 공동 문서
5. 미실행 검사, 남은 위험, 후속 과제

CI/CD 구성과 배포 Runbook은 이 하네스의 기본 검증 범위가 아니다.
