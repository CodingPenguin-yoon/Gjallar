# 아키텍처 설계와 발전 원칙

이 문서는 특정 패턴을 모든 프로젝트에 강제하지 않고 프로젝트에 적합한 구조를 선택하고 발전시키는 절차를 정의한다.

## 기본 관점

좋은 아키텍처는 폴더 이름이나 패턴의 수가 아니라 다음을 명확하게 만든다.

- 시스템이 해결하는 문제와 비범위
- 업무 책임과 도메인 경계
- 데이터와 상태의 소유권
- 의존성 방향과 공개 계약
- 트랜잭션과 정합성 경계
- 외부 시스템과 실패 격리
- 테스트 가능한 단위와 변경 비용

Layered, Domain-oriented, Clean, Hexagonal, DDD-lite는 필요에 따라 선택하거나 조합할 수 있다. 이름만 도입하고 책임과 의존성이 그대로라면 아키텍처 개선으로 보지 않는다.

## 아키텍처 선택 절차

1. 프로젝트 목적, 주요 사용자, 핵심 기능, 비범위를 확인한다.
2. 비즈니스 규칙, 데이터 정합성, 외부 연동, 운영 기간, 팀 규모를 분석한다.
3. 주요 도메인과 데이터 소유권 후보를 정리한다.
4. 현실적인 선택지를 적합도 순으로 최대 세 개 제시한다.
5. 각 선택지의 장점, 단점, 테스트 용이성, 변경 비용, 예상 구조를 비교한다.
6. 추천안과 감수할 단점을 명확히 제시한다.
7. 사용자의 결정을 받은 뒤 Architecture 문서와 필요 시 ADR을 작성한다.

하나의 선택이 명백하면 억지로 대안을 만들지 않고 그 근거와 위험을 설명해 확인받는다.

## 기술과 버전 선택

- 기술과 버전은 하네스가 미리 고정하지 않는다.
- 프로젝트 생성 시 공식 지원 상태, 안정성 또는 LTS, 호환성, 보안 지원, 배포 환경을 확인한다.
- 현재성이 중요한 정보는 공식 문서를 조회하고 확인일과 선택 이유를 Project Profile에 기록한다.
- 최신이라는 이유만으로 채택하지 않으며 기존 프로젝트에서는 현재 호환성을 우선한다.
- ORM, SQL 도구, 상태 관리, 라우터, UI 라이브러리도 같은 절차로 결정한다.

## 공통 구조 원칙

- 진입 계층은 입력 검증과 기술 문맥 변환을 담당한다.
- 유스케이스 계층은 업무 흐름, 권한, 트랜잭션, 외부 포트 호출을 조정한다.
- 핵심 비즈니스 규칙은 UI, HTTP, ORM, DB 드라이버에 직접 의존하지 않도록 한다.
- 데이터 접근과 외부 연동은 비즈니스 정책을 소유하지 않는다.
- 다른 도메인은 내부 구현이 아니라 승인된 공개 계약을 통해 상호작용한다.
- 단순 CRUD에는 불필요한 Port, Adapter, Aggregate, Event를 기계적으로 생성하지 않는다.

프로젝트의 복잡도가 낮다면 계층을 물리적으로 모두 분리할 필요는 없다. 책임과 의존성 규칙이 명확하면 같은 모듈 안에서도 단순하게 유지할 수 있다.

## 데이터와 트랜잭션

Architecture 문서에는 다음을 기록한다.

- 각 도메인이 소유하는 데이터와 상태
- 트랜잭션 시작·종료 위치
- 강한 정합성과 최종 정합성이 필요한 영역
- 재시도와 멱등성 기준
- 다른 도메인 데이터를 읽고 변경하는 계약
- migration과 호환성 전략

DB 모델을 도메인 계약이나 외부 API 계약으로 무심코 노출하지 않는다.

## ADR

다음처럼 되돌리기 어렵거나 장기 비용을 만드는 결정은 ADR로 기록한다.

- 주요 아키텍처 스타일과 도메인 경계
- 데이터 접근 방식과 데이터 소유권
- 외부 시스템, 메시지, 캐시, 스케줄러 도입
- 동기·비동기 전환
- 인증·권한 구조
- 주요 공개 계약과 배포 단위

ADR은 결정 배경, 기준, 검토한 선택지, 선택, 이유, 감수한 단점, 영향, 재검토 조건을 포함한다. 과거 ADR을 현재 상태에 맞춰 덮어쓰지 않는다.

## 기존 프로젝트 도입

`$legacy-adoption`은 현재 아키텍처를 사실대로 기록하는 절차다. 다음을 하지 않는다.

- 하네스 설치와 동시에 폴더 구조를 전면 변경
- 기존 기술을 일반적인 선호만으로 교체
- 모든 레거시 문제를 현재 작업의 범위로 확대
- 과거 코드 전체에 새 규칙을 소급 적용

기존 문제는 기준선과 위험으로 기록하고 새로 변경하는 영역부터 개선한다.

## 아키텍처 발전

아키텍처 변경은 `$architecture-evolution`을 명시적으로 사용한다.

```text
현재 구조와 동작 지도화
→ 변경 목적과 성공 기준
→ 목표 선택지 비교
→ 사용자 승인과 ADR
→ characterization test
→ 작은 수직 단계 전환
→ 단계별 검증과 복구 지점
→ 현재 상태 문서 갱신
```

일괄 재작성보다 Strangler, Branch by Abstraction, 모듈별 추출처럼 호환 가능한 점진 전환을 우선한다. 각 단계는 독립적으로 검증하고 되돌릴 수 있어야 한다.
