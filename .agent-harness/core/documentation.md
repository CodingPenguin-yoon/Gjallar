# 프로젝트 문서화 원칙

이 문서는 공동 프로젝트 지식과 개인 작업 지식을 분리하고, 필요한 문서만 코드와 동기화하는 기준을 정의한다.

## 문서의 목적

공동 문서는 나중에 본인이나 팀원이 프로젝트를 빠르게 이해하고 이어서 작업할 수 있게 해야 한다.

- 프로젝트가 해결하는 문제와 범위
- 승인된 기술과 아키텍처
- 도메인 경계와 데이터 소유권
- 공개 계약과 주요 실행 흐름
- 중요한 결정과 감수한 단점
- 실제 검증 명령과 알려진 위험

문서는 코드, Git diff, 커밋 메시지를 장황하게 복제하지 않는다.

## 문서 영역

### 공통 하네스

`AGENTS.md`, `.agent-harness/`, `.agents/skills/`는 공통 관리 영역이다. 프로젝트별 사실을 기록하지 않는다.

### 프로젝트 공동 문서

`project-docs/`는 Git에 포함하며 팀의 현재 기준 문서를 보관한다.

```text
project-docs/
├── project-profile.md
├── specifications/
├── architecture/
├── decisions/
├── domains/
├── flows/
├── api/
├── database/
└── plans/
```

필요한 디렉터리만 생성한다.

### 개인 문서

`.agent-local/`은 Git에서 제외한다.

```text
.agent-local/
├── learning/
├── notes/
├── research/
├── drafts/
└── plans/
```

개인 문서는 사용자가 요청한 학습 자료, 상세 설명, 조사, 임시 계획에 사용한다. 공동 결정의 유일한 근거나 필수 입력으로 사용하지 않으며 시크릿과 개인정보를 기록하지 않는다.

## 신규 프로젝트의 최소 문서

사용자와 설계를 합의한 뒤 다음 세 문서만 생성한다.

1. `project-docs/project-profile.md`
2. `project-docs/specifications/project-specification.md`
3. `project-docs/architecture/overview.md`

세 문서는 `DRAFT`로 시작하고 사용자 승인 후 `APPROVED`로 전환한다.

## 필요 시 생성하는 문서

- 중요한 설계 결정: `decisions/ADR-...md`
- 복잡한 도메인 경계: `domains/`
- 이해 비용이 높은 호출·데이터·실패 흐름: `flows/`
- 외부 소비자가 의존하는 계약: `api/`
- 중요한 스키마·migration·쿼리 구조: `database/`
- 고위험 작업: `plans/`

Runbook, CI/CD 문서, 모든 작업별 Change 문서는 기본 하네스 범위에 포함하지 않는다.

## 현재 상태와 과거 결정

- Project Profile, Specification, Architecture, Domain, Flow, API, Database 문서는 현재 상태를 설명한다.
- 현재 상태가 바뀌면 기존 문서를 갱신하고 중복 문서를 만들지 않는다.
- ADR은 결정 당시의 기록이므로 덮어쓰지 않고 새 ADR에서 대체 관계를 기록한다.
- 공유 Plan은 고위험 작업의 승인된 접근과 구현 후 차이를 기록한다.
- 일반 변경 이력은 Git과 PR이 담당한다.

## 문서 갱신 기준

코드 변경 후 다음 질문으로 문서 영향을 판단한다.

- 프로젝트 목적, 범위, 요구사항이 달라졌는가?
- 기술 스택, 실행 명령, 저장소 지도가 달라졌는가?
- 도메인, 데이터 소유권, 의존성 방향이 달라졌는가?
- 공개 API나 DB 계약이 달라졌는가?
- 주요 성공·실패·데이터 흐름이 달라졌는가?
- 기존 설계 결정을 대체하는가?

모두 아니라면 공동 문서를 수정하지 않는다. 문서를 수정하지 않은 이유를 긴 보고서로 만들 필요도 없다.

## 문서 작성 규칙

- 본문은 한국어로 작성한다.
- 파일명과 디렉터리는 영어 `kebab-case`를 사용한다.
- 코드 심볼, API, DB, 환경 변수는 원문을 유지한다.
- 기술 용어는 필요한 경우 처음에 한국어와 영문을 함께 적는다.
- 장기 문서에는 쉽게 바뀌는 줄 번호를 기본 사용하지 않는다.
- 전체 소스코드를 복사하지 않고 파일 경로와 주요 심볼, 책임을 설명한다.
- Mermaid는 관계나 흐름을 실제로 더 쉽게 이해할 때만 사용한다.
- 구현 전 예상 내용은 구현 후 실제 결과와 검증 상태에 맞게 갱신한다.
- 내부 비공개 사고 과정 대신 확인한 사실, 선택지, 결정과 근거를 기록한다.

## 문서 충돌

Specification은 의도된 동작, 코드는 실제 동작, 테스트는 검증된 동작을 보여준다. 서로 충돌하면 어느 하나를 조용히 맞추지 않는다.

1. 충돌 위치와 실제 영향을 확인한다.
2. 버그인지 오래된 문서인지 사용자와 판단한다.
3. 승인된 방향에 따라 코드, 테스트, 현재 상태 문서를 함께 맞춘다.

기존 프로젝트에 이미 유효한 `docs/` 체계가 있으면 내용을 중복 복사하지 않는다. Project Profile에서 기존 문서 위치를 지도화하고 `project-docs/`에는 하네스에 필요한 최소 진입점만 둔다.
