# 설계와 코드 품질 원칙

이 문서는 기술 스택과 관계없이 프로젝트 설계와 구현에 적용하는 공통 품질 기준을 정의한다.

## 품질 우선순위

1. 요구사항의 정확성 및 데이터 무결성
2. 보안과 공개 계약의 호환성
3. 책임, 도메인, 의존성 경계
4. 가독성과 변경 용이성
5. 테스트 가능성과 관찰 가능성
6. 성능과 자원 효율
7. 구현 속도와 코드 양

짧은 코드, 많은 패턴, 높은 테스트 커버리지 중 어느 하나만으로 품질을 판단하지 않는다.

## 가독성

가독성은 코드가 짧다는 뜻이 아니라 다음 질문에 빠르게 답할 수 있는 상태다.

- 이 코드가 해결하는 업무 문제는 무엇인가?
- 입력은 어디서 오고 어떤 형태로 바뀌는가?
- 상태와 데이터의 소유자는 누구인가?
- 성공과 실패는 어떤 경로로 전달되는가?
- 변경해야 할 책임은 어느 파일과 모듈에 있는가?
- 어떤 테스트가 이 동작을 보호하는가?

이를 위해 다음을 지킨다.

- 이름은 기술적 구현보다 도메인 의미와 역할을 드러낸다.
- 함수와 모듈은 하나의 주요 변경 이유를 갖는다.
- 상태 변경과 외부 효과를 숨기지 않는다.
- 조건 분기, 변환, 오류 처리는 독자가 따라갈 수 있는 순서로 표현한다.
- 주석은 코드가 하는 일을 반복하지 않고 이유, 제약, 감수한 단점을 설명한다.

## 책임과 경계

- 요청·UI 처리, 유스케이스 조정, 도메인 규칙, 데이터 접근, 외부 연동을 구분한다.
- 특정 프레임워크 계층 이름을 기계적으로 만들지 않고 실제 변경 이유를 기준으로 나눈다.
- 다른 도메인의 내부 구현, 저장소 구현, DB 모델을 편의상 직접 참조하지 않는다.
- 데이터 소유권을 가진 책임만 해당 상태를 변경한다.
- 공통 모듈은 소유자가 없는 비즈니스 로직의 피난처로 사용하지 않는다.
- 순환 의존성을 만들지 않으며 의존성 방향은 Architecture 문서에 기록한다.

## 단순성과 추상화

- 먼저 기존 구현, helper, interface, DTO, 예외, 테스트 패턴을 찾는다.
- 실제 중복과 동일한 변경 이유가 확인되기 전에 공통화하지 않는다.
- 미래 사용 가능성만으로 interface, base class, factory, event를 만들지 않는다.
- 단순한 기능에 모든 아키텍처 계층과 패턴을 기계적으로 생성하지 않는다.
- 새로운 의존성은 표준 기능과 기존 의존성으로 해결할 수 없는 경우에만 제안한다.

## 크기와 복잡도

공통 하네스는 고정된 파일·함수 줄 수를 하드 게이트로 사용하지 않는다. 대신 다음을 책임 집중 신호로 본다.

- 서로 다른 계층이나 도메인 책임이 한곳에 섞인다.
- 일부 동작만 독립적으로 테스트하기 어렵다.
- 기능을 추가할 때 dispatcher와 조건 분기가 계속 증가한다.
- 파일을 수정하려면 관련 없는 영역까지 이해해야 한다.
- HTTP/UI, DB, 외부 API, 비즈니스 규칙, 응답 변환을 함께 처리한다.
- 기존 대형 파일에 새로운 책임이 반복해서 추가된다.

분리가 필요하면 파일 수가 아니라 도메인 책임, 데이터 소유권, 트랜잭션, 외부 시스템, 변경 이유를 기준으로 나눈다. 프로젝트가 정량 기준을 원하면 Project Profile에 별도로 기록한다.

## 오류와 실패

- 현재 계층이 의미 있게 처리할 수 있는 오류만 잡는다.
- 원인을 보존하고 외부 오류를 내부 계약에 맞는 오류로 명시적으로 변환한다.
- broad catch 후 무시하거나 성공으로 바꾸지 않는다.
- 타임아웃, 재시도, 멱등성, 보상, 부분 실패 필요성을 검토한다.
- 사용자에게 보여줄 오류와 내부 진단 정보를 구분한다.

## 데이터와 보안

- 사용자 입력을 쿼리, 명령, 경로에 직접 연결하지 않는다.
- 데이터 검증과 권한 확인을 신뢰 경계에서 수행한다.
- 시크릿, 인증 정보, 개인정보를 코드·로그·문서에 기록하지 않는다.
- migration과 데이터 변환은 정합성, 호환성, 롤백 가능성을 함께 검토한다.
- 성능 변경은 추측이 아니라 측정과 실행 근거를 사용한다.

## 변경 규율

- 요청 범위를 만족하는 가장 작은 일관된 변경을 만든다.
- 범위 밖 대규모 리팩터링이나 포맷 변경을 섞지 않는다.
- 공개 계약과 기존 동작을 의도 없이 변경하지 않는다.
- 생성 파일은 생성 원본을 수정한다.
- 적용된 migration 이력을 덮어쓰지 않는다.
- 기존 사용자의 미완료 변경을 임의로 되돌리지 않는다.

## 재현 가능한 환경

- 프로젝트마다 언어와 도구 생태계에 맞는 격리·재현 환경을 사용한다.
- 런타임과 주요 도구 버전을 Project Profile에 기록한다.
- 의존성 lock 파일과 wrapper를 사용하고 불필요한 전역 도구 의존을 피한다.
- Codex도 프로젝트가 정의한 환경과 명령을 통해 실행한다.
- `.venv`, `node_modules`, build 산출물은 Git에 포함하지 않는다.
