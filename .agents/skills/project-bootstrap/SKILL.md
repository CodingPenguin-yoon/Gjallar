# Project Bootstrap

사용자와 프로젝트의 기준을 먼저 합의하고 승인된 문서가 준비된 뒤 구현을 시작한다.

## 준비

1. 루트 `AGENTS.md`를 읽는다.
2. `.agent-harness/core/workflow.md`, `architecture.md`, `documentation.md`, `verification.md`를 읽는다.
3. `.agent-harness/templates/project-docs/`의 세 기본 양식을 확인한다.
4. 저장소가 신규 또는 미설정 프로젝트인지 확인한다. 실질적인 기존 코드가 있으면 `$legacy-adoption`으로 전환한다.

## 인터뷰

한 번에 하나의 질문만 한다. 각 질문에 추천안, 이유, 감수할 단점을 함께 제시한다.

각 질문에는 현재 인터뷰 단계와 남은 핵심 질문의 예상 개수를 표시한다. 앞선 답으로 질문이 추가되거나 생략되면 예상치를 갱신한다.

다음 순서로 확정한다.

1. 해결할 문제, 주요 사용자, 성공 기준
2. 목표, 비목표, 범위, 핵심 요구사항
3. 품질·보안·데이터·운영 제약
4. 주요 도메인과 데이터 소유권 후보
5. 기술 스택과 재현 가능한 개발 환경
6. 아키텍처, 의존성 방향, 트랜잭션 경계
7. 테스트, Lint, 타입 검사, 빌드 명령
8. 프로젝트별 고위험 영역과 추가 승인 경계

이미 답한 내용은 다시 묻지 않는다. 코드나 파일로 확인할 수 있는 사실을 사용자에게 되묻지 않는다.

## 선택지 제시

- 프로젝트 적합도 순으로 최대 세 개까지만 제시한다.
- 명백한 추천안이 하나면 억지 대안을 만들지 않는다.
- 비용, 테스트 용이성, 변경 가능성, 팀 경험, 데이터·보안 영향을 비교한다.
- 기술 버전처럼 현재성이 중요한 정보는 공식 지원 자료를 확인한다.
- 확인한 버전, 근거, 확인일을 Project Profile에 기록한다.
- 사용자의 선택을 Codex의 추천과 구분해 기록한다.

선택된 preset만 읽는다.

- Spring Boot: `.agent-harness/presets/spring-boot.md`
- FastAPI: `.agent-harness/presets/fastapi.md`
- React: `.agent-harness/presets/react.md`

## 문서 작성

충분한 결정을 확인한 뒤 다음 문서를 실제 경로에 `DRAFT`로 작성한다.

1. `project-docs/project-profile.md`
2. `project-docs/specifications/project-specification.md`
3. `project-docs/architecture/overview.md`

빈 선택 항목을 추측으로 채우지 않는다. 미확정 사항은 명시적으로 남긴다. 중요한 결정이 필요할 때만 ADR을 추가한다.

기존 `README.md`와 `.gitignore`는 프로젝트 소유다. 덮어쓰기 전에 내용을 확인하고, `.agent-local/`과 선택된 스택의 로컬 환경·의존성·빌드 산출물 제외 규칙처럼 필요한 최소 변경만 적용한다. 선택되지 않은 기술의 패턴을 무더기로 추가하지 않는다.

## 승인 게이트

작성한 문서에서 다음을 사용자에게 요약한다.

- 프로젝트 목적과 비범위
- 선택한 기술과 버전
- 선택한 아키텍처와 감수한 단점
- 도메인, 데이터 소유권, 트랜잭션
- 실행할 검증 명령
- 미확정 사항과 위험

사용자가 승인하기 전에는 세 문서를 `APPROVED`로 바꾸거나 첫 구현을 시작하지 않는다. 승인 후 날짜와 승인자를 기록하고 구현 순서를 제안한다.

## 완료 결과

- 승인된 프로젝트 기준 문서
- 선택된 preset과 실제 검증 명령
- 필요한 ADR
- 구현 전 남은 결정과 위험
