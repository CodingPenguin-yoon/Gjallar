# Quality Review

구현자의 의도를 옹호하지 않고 사용자 요구사항과 실제 변경을 기준으로 확실한 결함을 찾는다.

## 리뷰 계약

- 기본적으로 파일을 수정하지 않는다.
- 사용자가 수정을 함께 요청한 경우에도 먼저 리뷰 결과를 분리해 보고한다.
- 스타일 취향보다 정확성, 위험, 변경 비용을 우선한다.
- 근거가 불충분한 가능성을 확정된 결함으로 보고하지 않는다.

## 준비

1. 사용자 요구사항과 인수 조건을 확인한다.
2. 루트 `AGENTS.md`, Project Profile, 관련 Specification·Architecture·ADR·Plan을 확인한다.
3. 전체 diff와 관련 코드, 테스트, 설정, 현재 상태 문서를 읽는다.
4. 실행된 검증과 미실행 검증을 구분한다.

## 검토 순서

1. 누락된 요구사항과 잘못된 동작
2. 데이터 손실, 정합성, transaction, 동시성, 멱등성
3. 인증·권한·시크릿·개인정보·입력 검증
4. 공개 계약 호환성과 외부 소비자 영향
5. 아키텍처, 도메인, 책임, 의존성 경계
6. 오류 변환, timeout, retry, partial failure
7. 가독성, 불필요한 추상화, 책임 집중, 중복
8. 테스트의 정상·경계·실패 흐름과 회귀 보호
9. 검증 결과의 정확한 보고
10. Project Profile과 현재 상태 문서의 동기화
11. 범위 밖 변경, 임시 코드, 디버깅 산출물

고정 LOC 기준으로 결함을 만들지 않는다. 코드 크기가 독립 테스트와 변경 이유를 방해하는 실제 근거가 있을 때만 책임 집중으로 보고한다.

## 심각도

- `Critical`: 데이터 손실, 보안 침해, 광범위한 장애, 복구 불가능한 변경
- `High`: 요구사항 실패, 주요 회귀, 정합성·권한 오류, 공개 계약 파괴
- `Medium`: 유지보수 위험, 의미 있는 테스트·문서 누락, 책임·오류 처리 문제
- `Low`: 실제 변경 비용을 줄이는 명확한 일관성 개선

## 발견 항목 형식

각 항목에 다음을 포함한다.

- 위치: 파일과 심볼
- 심각도
- 문제
- 실제 영향 또는 실패 시나리오
- 코드·테스트·문서 근거
- 권장 수정 방향

가장 심각한 항목부터 보고한다. 결함이 없으면 확인한 범위, 실행된 검증, 남아 있는 불확실성을 기록한다.

## 완료

리뷰 결과를 구현 흐름에 전달한다. 발견된 문제를 수정한 뒤에는 관련 검증과 문서 대조를 다시 수행한다.
