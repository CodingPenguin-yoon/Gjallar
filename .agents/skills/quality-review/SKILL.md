# Quality Review

사용자 요구사항과 실제 변경을 기준으로 확실한 결함을 찾는다. 기본적으로 파일을 수정하지 않는다.

## 실행 격리

1. delegation이 허용되고 사용 가능하면 구현에 참여하지 않은 `reviewer` subagent에 검토를 맡긴다.
2. reviewer에는 사용자 목표, 승인 범위, 관련 현재 문서, raw diff와 검증 출력만 전달한다. 구현자의 결론, 의심하는 결함이나 제안 수정안을 정답처럼 주입하지 않는다.
3. reviewer는 파일을 수정하지 않고 발견 사항만 반환한다. 수정은 리뷰 결과를 사용자가 확인한 뒤 별도 구현 단계에서 수행한다.
4. delegation을 사용할 수 없으면 동일 에이전트가 요구사항·현재 문서·raw diff부터 새 검토 pass를 수행하고, 결과에 독립 reviewer가 아닌 동일 컨텍스트 검토임을 밝힌다.

## 준비

1. 사용자 목표, 승인 범위와 비범위를 확인한다.
2. 관련 Specification, `ACCEPTED` ADR, `APPROVED` Plan과 현재 상태 문서를 확인한다.
3. 전체 diff와 관련 코드, 테스트, 설정을 읽는다.
4. 실행된 검증과 미실행 검증을 구분한다.

## 검토 순서

1. 최신 사용자 방향과 승인된 제품 목표 위반
2. 현재·과도기·목표 상태 혼동과 제거 대상의 무승인 확장
3. 누락된 요구사항과 잘못된 동작
4. 데이터 손실, 정합성, transaction, 동시성과 멱등성
5. 인증·권한·시크릿·개인정보와 입력 검증
6. 공개 계약 호환성과 외부 소비자 영향
7. 도메인 책임, 데이터 소유권과 의존성 방향
8. timeout, retry, partial failure와 오류 변환
9. 테스트 공백, 검증 보고와 현재 상태 문서 불일치
10. 범위 밖 변경, 임시 코드와 디버깅 산출물

스타일 취향이나 고정 LOC 기준으로 결함을 만들지 않는다. 근거가 약하면 가설로 표시한다.

## 보고

가장 심각한 발견부터 `Critical`, `High`, `Medium`, `Low`로 정리한다. 각 항목에 파일·심볼, 문제, 실패 영향, 근거와 최소 수정 방향을 포함한다. 발견이 없으면 확인 범위, 실행된 검증과 남은 불확실성을 기록한다.
