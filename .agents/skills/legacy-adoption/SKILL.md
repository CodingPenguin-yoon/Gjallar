# Legacy Adoption

기존 동작을 방해하지 않고 프로젝트의 현재 상태를 이해할 수 있는 최소 기준선을 만든다.

## 원칙

- 하네스 설치를 전면 리팩터링 작업으로 확대하지 않는다.
- 현재 코드를 이상적인 구조로 미화하지 않고 실제 상태를 기록한다.
- 기존 문서와 명령을 재사용하고 중복 체계를 만들지 않는다.
- 과거 코드 전체에 새 규칙을 소급 적용하지 않는다.
- 새로 변경하는 영역부터 공통 원칙을 적용한다.
- 아키텍처 변경은 `$architecture-evolution`에서 별도 승인받는다.

## 조사

1. 루트 `AGENTS.md`와 `.agent-harness/core/` 문서를 읽는다.
2. 저장소 구조, 언어, framework, lock·wrapper 파일, 실행 환경을 확인한다.
3. 기존 README, docs, ADR, API, DB, 테스트 문서를 검색한다.
4. 실제 formatter, Lint, 타입, 테스트, 빌드 명령을 확인한다.
5. 주요 진입점, 모듈·도메인, 데이터 소유권, 외부 시스템을 지도화한다.
6. 테스트가 부족하거나 변경 위험이 큰 영역을 기록한다.

확인 가능한 사실을 사용자에게 되묻지 않는다. 불명확한 결정은 한 번에 하나씩 질문하고 추천안을 제시한다.

## 기준선 문서

기존 문서를 중복하지 않는 범위에서 다음을 `DRAFT`로 만든다.

1. `project-docs/project-profile.md`
2. `project-docs/specifications/project-specification.md`
3. `project-docs/architecture/overview.md`

내용을 모두 복원할 수 없으면 확인된 사실, 추정하지 않은 빈 항목, 알려진 위험을 구분한다. 기존 `docs/`가 현재 상태를 잘 설명하면 Project Profile에서 해당 문서를 연결하고 내용을 복사하지 않는다.

`.agent-local/`이 Git에서 제외되는지 확인하고 기존 `.gitignore`를 보존하면서 필요한 항목만 추가한다.

## 사용자 확인

다음을 요약한다.

- 확인한 기술 스택과 버전
- 실제 실행 가능한 검증 명령
- 현재 아키텍처와 의존성
- 주요 도메인과 데이터 소유권
- 문서가 불완전한 영역
- 새 변경에서 우선 보호할 위험 영역

사용자가 사실 관계를 확인하면 해당 문서를 `APPROVED`로 전환한다. 불완전한 영역이 있다는 이유만으로 일반 유지보수를 막지 않는다.

## 점진 적용

- 일반 변경은 승인된 기존 패턴을 존중한다.
- 새 책임을 추가할 때는 더 명확한 경계를 사용한다.
- 위험한 레거시 변경은 characterization test와 `$task-planning`을 우선한다.
- 구조 개선 필요성을 별도 후속 작업으로 분리한다.
- 실제 아키텍처 변경 요청이 있을 때만 `$architecture-evolution`으로 전환한다.

## 결과

- 현재 상태를 사실대로 설명하는 최소 프로젝트 문서
- 검증 가능한 프로젝트 명령
- 선택된 preset
- 위험 기준선과 점진 개선 후보
- 기존 문서 재사용 지도
