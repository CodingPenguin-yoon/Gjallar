# Task Planning

고위험 작업의 현재 상태, 선택, 단계, 검증, 복구 방법을 구현 전에 명확히 한다.

## 준비

1. 루트 `AGENTS.md`와 `.agent-harness/core/workflow.md`를 읽는다.
2. `project-docs/project-profile.md`와 관련 Specification, Architecture, ADR을 읽는다.
3. `.agent-harness/templates/project-docs/plans/plan-template.md`를 확인한다.
4. 관련 코드, 테스트, 설정, 공개 계약, 데이터 구조를 조사한다.

## 위험도 확인

작업이 실제로 고위험인지 근거를 기록한다. 파일 개수와 코드 줄 수만으로 판단하지 않는다.

조사 결과 일반 작업이면 공유 Plan을 만들지 말고 그 이유를 짧게 보고한 뒤 일반 흐름으로 전환한다.

## 현재 상태 조사

- 현재 관찰 가능한 동작과 진입점
- 관련 호출·데이터·실패 흐름
- 도메인과 데이터 소유권
- 트랜잭션, 동시성, 재시도, 멱등성
- 외부 소비자와 호환성
- 기존 테스트와 검증 명령
- 알려지지 않은 항목과 rollback 제약

확인하지 못한 사실을 계획의 전제로 만들지 않는다.

## 계획 작성

`project-docs/plans/YYYY-MM-DD-<task-name>.md`를 `DRAFT`로 작성한다.

- 목표, 범위, 비범위, 인수 조건
- 위험도와 실패 영향
- 아키텍처·데이터·보안 영향
- 필요한 선택지와 추천안
- 작은 수직 구현 단계
- 단계별 책임과 예상 파일
- 테스트·검증 계획
- 문서 영향
- rollback, roll-forward, 중단 기준

선택지는 적합도 순으로 최대 세 개만 작성하고 명백한 결론에는 가짜 대안을 추가하지 않는다.

## 승인과 실행

- 새로운 주요 결정이 있으면 한 번에 하나씩 사용자에게 묻는다.
- 승인 전에는 되돌리기 어려운 구현을 시작하지 않는다.
- 사용자가 이미 같은 방향을 명시적으로 승인했고 새 결정이 없으면 반복 승인을 요구하지 않는다.
- 승인 후 Plan을 `APPROVED`로 바꾸고 작은 단계로 구현한다.
- 각 단계에서 관련 검증을 실행하고 실패하면 다음 단계로 진행하지 않는다.

## 구현 후

- 계획과 실제 구현의 차이와 이유를 기록한다.
- 최종 검증 결과와 남은 위험을 기록한다.
- `$documentation-sync`로 실제 변경된 현재 상태 문서만 갱신한다.
- 고위험 구현 완료 전 `$quality-review`를 수행한다.
- 완료되면 Plan 상태를 `IMPLEMENTED`로 변경한다.
