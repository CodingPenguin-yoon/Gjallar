# Task Planning

고위험 변경을 구현하기 전에 현재 상태, 선택, 단계, 검증과 복구 방법을 합의한다.

## 조사

1. 사용자 목표와 `project-docs/project-profile.md`를 확인한다.
2. 관련 Specification, Architecture, 최신 `ACCEPTED` ADR과 유효한 Plan만 읽는다.
3. 관련 코드, 테스트, 공개 계약, 데이터와 외부 효과를 조사한다.
4. 현재 상태, 임시 호환 상태와 승인된 최종 목표를 구분한다.
5. 데이터 소유권, transaction, 동시성, 멱등성, 권한, 외부 소비자와 rollback 제약을 확인한다.

조사 결과 일반 작업이면 공유 Plan을 만들지 않고 그 근거를 보고한다.

## Plan

고위험이면 `project-docs/plans/YYYY-MM-DD-<task-name>.md`를 `DRAFT`로 작성한다. 기존 관련 Plan이 있으면 중복 문서를 만들지 말고 그 상태와 범위를 먼저 확인한다.

Plan에는 다음을 포함한다.

- 사용자 목표, 범위, 비범위와 인수 조건
- 현재·과도기·목표 상태와 상위 제품 방향
- 영향받는 계약, 데이터, 보안, 도메인과 외부 시스템
- 의미 있는 선택지, 추천안과 감수할 단점
- 되돌릴 수 있는 작은 구현 단계와 단계별 검증
- rollback 또는 roll-forward, 중단 기준과 남은 불확실성
- “이 승인은 X를 의미하며 Y를 의미하지 않는다” 형식의 승인 문장

승인 전에는 되돌리기 어려운 구현을 시작하지 않는다. 사용자가 승인 문장에 동의하면 승인자와 날짜를 기록하고 상태를 `APPROVED`로 바꾼다.

## 구현 후

계획과 실제 구현의 차이, 최종 검증과 남은 위험을 기록한다. 관련 현재 상태 문서만 코드와 맞추고, 구현과 분리된 `$quality-review`가 끝난 뒤 Plan 상태를 `IMPLEMENTED`로 변경한다.
